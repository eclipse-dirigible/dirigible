## Harmonia runtime UI (`template-application-ui-harmonia-java` + `template-form-builder-harmonia`)

The runtime UI stack for generated applications: they render as a self-contained **Alpine.js + Harmonia SPA** (client-routed by Pinecone in hash mode, no iframes/`postMessage` hubs), served at `/services/web/<project>/gen/<model>/index.html`, talking to the **reused** generated Java REST controllers over a `fetch` client. The AngularJS IDE is untouched; the application layer ships this stack only. `template-application-ui-harmonia-java` (registered on `platform-templates` as "Application - UI (Harmonia) - Java") emits the view types (list, manage, setting, master-detail, document, calendar, slots, reports) + built-in **Process Inbox** (`/inbox`) and **Documents** (`/documents`) shell sections + inline process-task surfacing; `template-form-builder-harmonia` ("Harmonia Generator from Form Model", extension `form`) is the runtime form generator. The stack is embedded as **webjars** via `components/resources/application-core` (`harmonia.version`, `alpinejs.version`, `lucide.version`, `pinecone-router.version`, `i18next.version` in the root `pom.xml`), served version-less through webjars-locator at `/webjars/<name>/dist/...`; a version bump is a pom-only change. Report charts use Harmonia's native `x-h-chart-*` SVG charts.

### Colours come from the THEME - never from a CSS override (normative)

**Never override a Harmonia colour in a stylesheet of this repo.** Colours in Harmonia are owned by
the **theme**: `--primary`, `--negative`, `--positive`, the surface and border tokens and every
variant built on them. If a colour has to change, **the theme changes** - upstream in the design
system, where every component that reads that token changes with it. A rule in
`application-core/shell/css/app.css` (or any module stylesheet) that sets a `color`,
`background-color`, `border-color` or `fill` to a literal, or that re-points a Harmonia token, is
refused in review however narrowly it is scoped.

The reasoning, because the tempting case always looks local: an override is scoped to the one
selector whose look the author happened to be looking at, so the SAME semantic colour then renders
two different ways in one application - the overridden badge beside a destructive button, an error
border, a chart series, a toast - and nothing anywhere records that they were meant to be one
colour. It also silently stops tracking the design system: the next version ships a corrected
`--negative` and every component picks it up except the one pinned here. A theme change has neither
property.

This holds even when a measurement is on the author's side. **A contrast figure is a guideline, not
a verdict**: WCAG's 4.5:1 is what we steer by, not a rule that must be satisfied 100% of the time,
and "below 4.5:1" does not by itself mean a colour is unreadable or that it must change. So a
contrast finding is an argument to put to the design system, not a licence to patch a colour here -
and whether it is acted on at all is the theme's call. (#7704 was exactly this shape and was
withdrawn: a scoped `[data-slot="badge-indicator"][data-variant="negative"]` override of
`--negative`'s rendered value, for a 3.94:1 reading on the notification badge.)

What a module stylesheet legitimately owns is layout and non-colour affordance - spacing, sizing,
the drag-grip and overflow rules already in `app.css` - and even there a colour value is written as
`var(--token)`, never as a literal.

### The Harmonia rules live upstream - the skill is the rule set

**Do not write Harmonia markup from memory or from the examples already in this repo.** The single source of truth for every `x-h-*` directive, attribute, modifier, variant and utility class is the Harmonia skill, version-matched to `harmonia.version`:

- Install it as a Claude Code plugin: `/plugin marketplace add codbex/harmonia` then `/plugin install harmonia@codbex`. The same files ship inside the `codbex__harmonia` webjar under `skills/harmonia/` (`SKILL.md`, `references/<component>.md`, `references/utility-classes.md`, `references/migration.md`) and in the `codbex/harmonia` repo.
- Before a version bump read `references/migration.md` (breaking changes by version) and the CHANGELOG; before touching a component read its reference; before using a utility class confirm it is in `references/utility-classes.md` - a class Harmonia does not ship silently does nothing (use an inline `style` for a one-off value, a rule in the module's own `css/app.css` when several sites share it). Where an example in this repo contradicts the skill, the example is wrong.
- Harmonia's example apps (`docs/public/templates/{granite-erp,onyx-chat,quartz-docs,slate,ember}` in the Harmonia repo) show the canonical composition of an app shell: sidebar destinations are `x-h-sidebar-menu-nav`, every icon is `<svg x-h-lucide role="presentation" data-lucide="...">`, dialogs pad through `x-h-dialog-content`, cards through their slots, the theme control is a Light / Dark / Auto radio menu.

`HarmoniaContractIT` (`tests-integrations`, HTTP-only, in the PR smoke gate) is the guard: it reads the directive registry out of the webjar's `dist/harmonia.min.js` and the class allowlist out of its `skills/harmonia/references/utility-classes.md`, then scans every Harmonia shell page and the rendered output of the generated-app templates for an unregistered `x-h-*`, a non-shipped class, an `<i x-h-lucide>` placeholder or an unknown button/badge variant. A failure names the resource and the token.

### A bug in Harmonia is reported upstream, never fixed here (normative)

**When Harmonia itself misbehaves, do not fix it or work around it in this repo. Write the issue and ask the user to file it in <https://github.com/codbex/harmonia/issues>.** "Itself" means the markup follows the version-matched reference (`skills/harmonia/references/<component>.md`) and Harmonia still does not do what the reference says, or a directive throws, or a component renders wrong with the theme untouched. If this repo's markup contradicts the reference, the bug is ours and it is fixed here. The 3.6.0 bump is the worked example: the generated slots page passed `slots: []` with no `fillEmptyDays` and only showed free slots because of Harmonia's bug #144, so fixing that bug upstream broke the page, and the fix belonged in the template.

"Not here" rules out every local form of a fix: a stylesheet rule (see the colour rule above), a re-registered or wrapped `Alpine.directive('h-...')`, a DOM fix-up after Harmonia has initialised, a listener that undoes what a component did, or a patched or vendored copy of `harmonia.js`. A local patch covers only the surfaces its author was looking at, it keeps running after the upstream fix ships, and from then on it fights that fix. #7754 shows the better route. Its issue proposed a wheel guard in the shared shell runtime. Instead it was filed upstream as codbex/harmonia#147, and the 3.6.0 bump fixed every number input, with nothing to remove here.

Write the issue for a maintainer who has never seen Dirigible, in the shape of codbex/harmonia#144, #145 and #147:

- **Title**: the observable defect in one sentence (`An empty slots array shows the generated schedule`).
- **`## Issue`**: what happens, under which condition, and which documented behaviour it contradicts (quote or link the component's page). Give the Harmonia version, and the browsers and OS where it reproduces and where it does not.
- **A minimal, isolated reproduction**: a self-contained HTML snippet that uses only Alpine and Harmonia (no Dirigible shell, no generated app, no Velocity, no `App.*`), with the fewest elements that show the defect, plus the steps that trigger it (`press Next, then Reload slots`). Run it against the pinned version (the `dist/` of the `codbex__harmonia` webjar) before handing it over: a reproduction that does not reproduce costs the maintainer more than none.
- **`## Expected`**: what should happen instead, phrased as Harmonia's contract rather than as Dirigible's need.
- `Related to Dirigible issue #NNNN` when one exists.

Hand the issue over as a ready-to-paste title and Markdown body, then stop. Never file it yourself (no `gh issue create --repo codbex/harmonia`): the user files it. Dirigible work that depends on the fix waits for the Harmonia release and the `harmonia.version` bump that brings it, and the hand-over says so. An interim workaround is the user's explicit call, never the default. If they ask for one, it carries a comment naming the upstream issue, so the bump that ships the fix removes it. A regression that a version bump introduces is handled the same way: report it, do not patch around it here.

### Dirigible-specific facts the skill cannot know

- **One shared shell runtime, never copied per project.** It lives once at `/services/web/application-core/shell/` (`components/resources/application-core/.../application-core/shell/`: `app.js`, `services/*`, `stores/*`, `components/layout/appShell.js`, base/page components, `css/app.css`, the Inbox/Documents/Reports/notfound views). The generated per-project shell and the platform shells (`resources-application`, `-admin`, `-personal`, `-partner`, `-monitoring`, `-database`, `-builder`, `-home`, the tenant picker in `security-oauth2`) load it by absolute URL; `template-application-ui-harmonia-java` only **generates** the model-specific files (`index.html`, `config.js`, `dashboardPage.js`, `_settings.html`, `_dashboard.html`, per-entity pages). Do NOT re-add per-project copies of the shared files. **Because it is shared, its page contract is public across generated vintages (#7427):** a project's `index.html` is rewritten only by an explicit Generate, so a platform upgrade swaps this runtime under pages generated months earlier. The properties a page binds and the `x-ref` names the runtime reaches for must stay alive when renamed - `appShell.js` keeps `hiddenPanels.left` / `isOpen` / `sidebarPanel` / `overlay` from before #7400 as aliases - and `ShellRuntimeVintageIT` is the guard: it puts the PREVIOUS template's rendered page (a fixture, not a regeneration) in the registry over the generated one and drives it in the browser, because every other Harmonia IT regenerates the page and so never sees old page + new runtime.
- **Theme = Harmonia's colour-scheme API, three modes.** Harmonia persists the selection under `codbex.harmonia.colorMode` (default `auto`, the OS scheme), applies the `.dark` class itself and keeps every same-origin frame and browser tab in sync itself - nothing in this repo seeds the key or listens to `storage` events, and nothing may toggle `.dark` by hand. The shared `$store.theme` (`shell/js/stores/theme.js`) exposes `mode` (`light|dark|auto`, a getter/setter over `Harmonia.get/setColorScheme`) and `icon`, and re-syncs through `Harmonia.addColorSchemeListener((scheme, mode) => ...)`; every toolbar carries the same control - an icon button that is an `x-h-menu-trigger.dropdown` opening three `x-h-menu-radio-item`s bound to `$store.theme.mode`. Pages that load no shell runtime (home, tenant picker) carry the same getter/setter locally.
- **Toasts go through the public `$notifications` magic.** A magic lives on an Alpine component scope, so the root component that renders the `x-h-notification-overlay` hands it to the shared store once at init (`Alpine.store('notifications').attachToaster(this.$notifications)`); `announce()` records the bell entry first and raises the toast through `add({ template: 'toast', position, timeout, data })`. Never reach into Harmonia's private `_h_notifications` store.
- **`format.js` (`window.HarmoniaFormat`) stays the date/number engine**, not `x-h-date-format`: it preserves Java `DecimalFormat`/`DateTimeFormatter` pattern semantics and is dependency-free for the BPM task-form iframe. `HarmoniaDateFormatIT` asserts the `x-h-date-picker-popup="HarmoniaFormat.pickerConfig()"` contract. `window.HarmoniaFormat`, `window.HarmoniaCalendar` and `window.HarmoniaBranding` are Dirigible globals that only share the word; Harmonia itself sets only `window.Harmonia`.
- **`codbex.harmonia.language` is shared as a localStorage key only.** Dirigible drives i18next through its own `shell/js/services/i18n.js` and does not load `harmonia-i18next.min.js`, so `x-h-translate`, `$t` and `$i18n` are unavailable in the shells; use `T(key, fallback)`.
- **Velocity vs Alpine `$` is the #1 trap in the generated shell templates.** `index.html.template` and `dashboardPage.js.template` are rendered by Velocity, which parses `$`-references everywhere - inside HTML comments and JS string bodies too. An Alpine magic like `$store`/`$notifications`/`$nextTick` is fine as a bare reference, but a method call with arguments or trailing statements makes Velocity choke (`Encountered "..."`). Keep `$store.x` to bare refs / no-arg calls, escape with `#set($dollar='$')` + `${dollar}store` for anything richer, or move the logic into a copied (non-Velocity) JS file or an appShell method.
- **Put cross-scope shell state in an Alpine store, not the `app` component.** An eager `x-show` on a toolbar element evaluated before the `app` scope resolved threw "theme is not defined" intermittently; stores (`$store.theme`, `$store.notifications`, `$store.currentUser`, `$store.reports`, `$store.processTasks`) resolve from any scope at any time.
- **The tenant chip is ONE fragment, mounted nine times (#7459).** `shell/js/stores/tenant.js` (`$store.tenant`) reads `GET /services/security/tenant-selection/current` and fetches `shell/views/_tenant-menu.html` into `markup`; every shell mounts it with two lines - the store `<script>` after `stores/currentUser.js`, and `<div class="hbox items-center gap-2" x-show="$store.tenant.visible" x-cloak x-html="$store.tenant.markup">` right before `#user-menu-trigger` - in the seven platform shells, Home (which has no `T`, so the store translates through its own `t()` with the English fallback) and `template-application-ui-harmonia-java`'s `index.html.template`, so a regenerated application carries it with no hand edits. `x-html` initializes the injected tree, so the fragment's own `x-if`/`x-for`/Harmonia directives bind (the `settingsPage.js` pattern). The fragment renders a read-only `x-h-badge` (nothing to switch to: a `SUBDOMAIN` instance, a single-tenant user, staff in the default tenant) or an `x-h-button` + `x-h-menu` of the offered tenants, both under `id="tenant-menu-trigger"`; a switch is the picker's own `POST` followed by `location.replace(location.pathname)` on the shell root - of `window.top` when embedded same-origin - because the selection applies from the next request and the current route may not exist in the other tenant. Hidden entirely when `multitenant` is false. There is still no header extension point; this is the shape a shared header piece takes until there is one. `HarmoniaContractIT` scans the fragment through its `application-core/shell/views/*.html` pattern.
- **The Users section is the second shared fragment (#7498)**, mounted the same way as the tenant chip: `shell/js/stores/tenantUsers.js` (`$store.tenantUsers`) fetches `shell/views/_tenant-users.html` into `markup`, and a page renders it with `x-html` - the application shell's Settings pane and the generated shell's Settings. Every binding in the fragment goes through `$store.tenantUsers`; refusals are shown from the endpoint's `reason`, never its raw text. The mounts use only `visible`, `markup` and `load()`, so the section can change without touching a shell or a generator template. Two patterns it settled: a multi-select is an `x-h-select` whose `x-model` is an array (the input switches mode on the model's shape - set it before the select initializes), and a dialog's checkboxes bind an array that always exists (`editRoles`), because the dialog stays in the DOM and Alpine evaluates its bindings while it is closed; each dialog is `x-h-dialog-overlay :data-open` with Esc and the overlay click wired by the page.
- **The Print Templates section is the third shared fragment (#7755)**, same mounting: `shell/js/stores/printTemplates.js` (`$store.printTemplates`) fetches `shell/views/_print-templates.html` into `markup`. Two patterns it settled: a store has no `$watch`, so the two `x-h-select`s bind `x-model` to the store's `entity`/`language` and an `Alpine.effect` in `init()` re-reads the languages or the catalogue when the choice changes - with the choice being read kept in closure variables (not store properties), so the effect tracks only the choice; and a PDF preview opens its tab synchronously in the click (`window.open('', '_blank')`) and navigates it to the blob URL after the render, because a tab opened after an await is what popup blockers swallow.
- **`x-show` only hides - Alpine still evaluates the inner bindings.** Use optional chaining (`selected?.<field>`) in property panes that render before a selection exists, and `<template x-if>` for embedded preview iframes.
- **Authored labels are escaped for every JS/Alpine interpolation (#7294).** `ModelParameterProcessor` produces `widgetLabelJs`; the templates set `$plabel`/`$clabel`/`$elabel` from it and use it in every `T(...)` argument, `:placeholder`, column/label map and chart series name. Never substitute the raw `widgetLabel` inside an expression: an apostrophe would close the JS string and break the whole Alpine expression.
- **A boolean field's checkbox sits in a plain box** (`<div class="hbox items-center gap-3"><span x-h-checkbox>...`) because an `x-h-field` stretches a direct child to full width (#7103); `IntentEmissionCoverageIT` asserts the wrapper on the power and the personal form.
- **Read-only / system fields render in a headerless `x-h-card` above the action buttons** (`x-h-card` > `x-h-card-content` with a `grid-cols-1 sm:grid-cols-2 gap-x-4 gap-y-2`; label `text-xs text-muted-foreground`, value `text-sm`; shown on edit and only when populated) - wired in `manage/form-view` + `document/document-view`. **Every value shown in a read-only card goes through the shared `basePage.fieldDisplay(value, widget, floatPattern, options)`** (#7522) via each view's `#valueDisplay` / `#valueGate` macros: option labels, the instance date format, a float's own pattern (an integer gets none), a checkbox's translated state (its options are the two states), `''` for empty so the row hides on the formatted output, plus the `canSee` gate for a `roleRead` field. The three form views' Details cards and the three document views' cards (Details, frozen header) all use it; never print `form.X` raw there, and do not reintroduce per-page formatter copies - the three `headerDisplay` copies it replaced each threw on a DROPDOWN. `HarmoniaFieldDisplayIT` runs the helper. **Document layout roles:** a field with intent `documentTitle: true` -> `widgetType="DOCUMENT_NUMBER"` renders in the form title, a to-one with `documentStatus: true` -> `widgetType="DOCUMENT_STATUS"` renders as a read-only `x-h-badge` pill in the title bar (`statusVariant(text)` maps keywords to the badge variants).
- **`widgetSize` is a plain integer column count 1..12** (the intent's `size:`, validated at parse), mapped to `sm:col-span-N` on the 12-column form grid. Old `.edm` files with the legacy Fundamental string (`fd-col-md--2 fd-col--3`) render a broken width class.
- **The document conversation thread** (`documentItemsLayout: chat`) is `x-h-bubble` messages (`data-align` by author, `warning` variant for an internal memo) in a `role="log"` container, with an `x-h-input-group` composer whose textarea keeps `x-model="chatDraft"` and whose send button calls `sendMessage(chatDraft)` - both asserted by `IntentEmissionCoverageIT` and walked by the Playwright `my.js` flow.
- **The shell is model/runtime-driven:** a home Dashboard (`/`, `/dashboard`) with report-attached KPI widget tiles + custom widget tiles + per-report preview tiles (no auto per-entity record-count tiles); sidebar sections Application / Entities / Reports (reports are discovered at runtime by the `reports` store); a route-derived breadcrumb (`navLabels` from the generated `window.__harmoniaNav`); a user menu, the notifications bell (the `notifications` store; `processTasks.syncTasks()` surfaces BPM tasks, polled every 30 s + on `pinecone:end`) and the theme menu; Settings pinned to the sidebar footer.

### Generated-app contracts (not Harmonia, but the templates depend on them)

- **REST path must use the Java-sanitised names.** `restBase` is `/services/java/<project>/gen/${javaGenFolderName}/api` and each page's `apiPath` is the **relative** `/${javaPerspectiveName}/<Entity>Controller`; the fetch client prepends `restBase` exactly once. Use `javaGenFolderName`/`javaPerspectiveName` (e.g. `sales-order` -> `sales_order`), not the raw `genFolderName`/lowercased perspective.
- **`{ baseUrl: '' }` means "URL is absolute, prepend nothing".** The fetch client checks `opts.baseUrl !== undefined`, not truthiness - passing `''` with a relative path (or omitting it with an absolute path) is the classic doubled-URL bug. Entity pages use a relative `apiPath` and no override; absolute URLs (relationship dropdowns, the detail registry) pass `{ baseUrl: '' }`.
- **Date/time widgets need conversion both ways.** `toPayload()` turns an HTML `date`/`datetime-local` value into a full ISO instant so a Jackson `java.time.Instant`/`Timestamp` field binds (empty -> `null`, a bare `TIME` passes through); `toDateInput()` slices the backend's value back - and the Java controller serializes `java.time` as **arrays** (`LocalDate` -> `[y,m,d]`, `LocalDateTime` -> `[y,m,d,h,mi,s,ns]`) and `Instant` as a numeric epoch, so `toDateInput()` handles arrays/numbers/strings. A relationship FK comes back as a **number** while an option's `data-value` is a string: stringify on load (`form.X = String(record.X)`) or the `x-h-select` matches no option.
- **A `number: { stampOn: issue }` value is never printed raw (#7722).** Until the issue step stamps it the column holds a UUID placeholder, and `HarmoniaFormat.documentNumber(v)` (format.js) is the one renderer: a UUID becomes the translated draft marker (`application-core:shell.defaults.draftNumber`, "(draft)"), anything else passes through. Callers opt in by flag, never by sniffing every value - a plain `type: uuid` field shares the shape: the field itself carries `numberStampOnIssue` (list cells, record sheets, `fieldDisplay(..., 'DOCUMENT_NUMBER')`, the summary line, export columns' `documentNumber`), a relation labelled by one carries `widgetDropDownDocumentNumber` (the per-page `#labelOf` / `#labelRows` macros, `basePage.documentNumberLabels`, a `lookup.documentNumber` spec that `detailPanel` and the prompt dialog honour), a `show:` column of one `documentNumber`, a task-form control `documentNumber`, an Inbox subject field kind `docnumber`. A new surface that prints a number or a relation label goes through the same flags.
- **Master-detail is registry-driven.** A master browses on the manage list (its record sheet shows the master's own fields only, #7390) and its form - at `/:id/preview` and `/:id/edit` - renders one `detailPanel` per `App.detailsFor(<master>)` entry, each detail row offering its own actionable process tasks on Preview too; each detail self-registers via `App.registerDetail(...)` (relative `apiPath`); the detail list filters via the controller's `?<masterEntityId>=<id>` query.
- **A parent FK implied by the navigation context renders locked, not free (#6551).** When the opening URL names the parent FK (`?<Fk>=<id>`), the form renders that relation as the referenced record's label, read-only (`isContextLocked(name)` / `contextLabel(value, options)` on `baseFormPage`); the shared `detailPanel` carries the master FK on edit/preview as well as create.
- **The `.form` runs the existing AngularJS `code` via compat shims, and the page is self-contained.** `template-form-builder-harmonia` runs the `.form` `code` as the body of `formController(ctx)` and defines `$scope`/`$http`/`NotificationHub`/`DialogHub` shims; the page loads only `form.js` + its own minimal fetch client, because a BPM task form opens standalone in an iframe where the SPA shell assets are absent.
- **A standalone page must bootstrap `App.config.projectName` before loading `i18n.js`**, or every module-authored label silently stays English (the report page and the task form set it in a one-line inline script). A value MATCHED against data (a status step's `label`) stays untranslated and gets a separate translated `title`.
- **A generated page never shows `e.message`; the shared `apiErrors` gate is the only path from a REST error body to a banner** (`refusalText` / `refusalMessageFor` / `namedProperty` + `messageWithLabels`; standalone pages load `shell/js/services/apiError.js` by absolute URL). `IntentEmissionCoverageIT` walks every emitted `.js`/`.html` under `gen/` and fails on `(e && e.message)` / `String(e.message`.
- **Intent glue handlers are self-describing `@Component`s, not class-level `@Listener`/`@Scheduled`** (those SDK annotations are `@Target(METHOD)`).
- **The full-stack model template MUST merge the schema layer** (`template.js` = `template-application-schema` + REST-java + Harmonia UI): the client-Java `JavaEntityManager` only registers an `@Entity` against an existing table, `TableCreateProcessor` creates it.
- **The process trigger writes its process stamp via a targeted update (no event, no full row)**: `repository.updateProperties(id, {"ProcessIds": ..., "ProcessId": processId})` after `Process.start`, with the minted `businessKeyStrategy` value persisted before the start and every process variable riding the start payload; a `null` instance id is logged and not written; a failed write-back cancels the just-started instance (#6815); the guard is per process over `ProcessIds` (`ProcessStamps.has`, #6862) and the generated repository skips `enforceChecks` for a targeted write that touches only platform-owned columns.
- **Documents/CMS path contract (`/services/documents`, `engine-cms`'s `DocumentsEndpoint`).** The CMS query layer does not decode an encoded slash, so build `?path=` with literal slashes (`p.split('/').map(encodeURIComponent).join('/')`). Rename is `PUT {path,name}`; delete is `DELETE` with a JSON body of absolute paths; create a folder with `POST /folder {parentFolder,name}`; upload is multipart under `file`; preview/download are `GET /preview|/download?path=`; zip is `GET|POST /zip?path=`. `__internal` is never listed (403), `__EXPORTS` needs ADMINISTRATOR/OPERATOR. Content types can be overridden with a `DocumentContentTypeResolver` bean.
- **A completed BPM task re-reads the page through `harmonia:tasks-changed`, never through a single re-fetch (#7612).** The `processTasks` store compares the task set per process on every inbox reading and raises the window event naming the processes that differ; after a task form closed on its own `harmonia.form.close` (a completion - the dialog's X passes nothing) it re-reads again on a bounded schedule (2/5/10/20 s, stopping once the process shows its next task), because the chain behind a user task (number, status, totals, the Snapshot copy) runs behind `flowable:async` boundaries and a re-read on completion alone races it. Pages subscribe with `basePage.onTasksChanged(() => <record>.ProcessId, reload)` - filtered by the record's own process, dropped in `destroy()` - and the shared `detailPanel` subscribes through its `master` argument, so the form hands it `form`. Background re-reads are **quiet** (`load(true)` / `loadRecord(true)` / `loadItems(true)` keep the rows on screen) and a document/record page skips its header while `isDirty()`; every detail panel also carries a Refresh action (`refresh()`, `defaults.refresh`). `HarmoniaTaskRefreshIT` runs the store and the mixin in GraalJS and sweeps the templates.
- **A BPM task's name travels with its translation key - the shell never derives one.** The generated `.bpmn` declares its module's catalog once on the `<process>` element (`taskLabelCatalog`, minted by `IntentNaming.processTaskCatalog`); `BpmInboxEndpoint` serves every task a `nameKey`/`processDefinitionNameKey`; the client renders `T(task.nameKey, task.name)` through the `processTasks` store. Do not reintroduce a per-project `processTaskKeys` reverse map.

- **A `dependsOn` watcher is registered BEFORE the catch-up, never after the awaited loads (#7604).** The generated document and form pages used to register `$watch('form.<trigger>')` only after `await loadOptions()` / `loadHeader()`, so a trigger picked during the page's first load - seconds wide on a tenant whose shell issues one GET per open Inbox task - was never seen by any watcher, and the init-time catch-up ran with `adjust=false` (filter the options, write nothing): the customer was picked, the invoice's Language stayed empty and the PDF printed in the wrong language. The order is now watcher first, then one catch-up for a trigger already in the form, with `adjust` decided by WHO put it there: a value the page itself hydrated (the stored record on edit/preview, a URL prefill) only filters the options - a stored value is never touched - while a value that arrived any other way during the loads is the user's pick and applies its prefill. Registering the watcher before the catch-up leaves no gap between the two. Both templates that carry the shape (`document-page.js.template`, `form-page.js.template`) follow it; a new page with a trigger watcher must too.
- **A `dependsOn` picker never shows the unnarrowed list, not even while the page loads (#7669).** `loadOptions()` used to fetch the whole target table for every dropdown, the cascade narrowing it only after the record load finished - so the picker spent the whole init offering rows the trigger goes on to refuse, and a user who picked one got a server rejection. The per-property fetch now lives in its own `loadAllOptions<Name>()`; `loadOptions(deferDependsOn)` calls `refreshOptions<Name>()` (narrowed while the trigger holds a value, whole while it does not) for a depends-on dropdown, and `init()` passes `deferDependsOn` so the list is decided once - after the record/URL prefill has put the trigger in the form - by the same catch-up that registers the watcher. No trigger at all means the whole list, and clearing the trigger returns to it. The same init also stopped resolving off-filter stored keys one `await` at a time: `ensureFilteredCurrent` now issues them together through `Promise.all`, so a MULTISELECT holding a few hundred keys costs one burst instead of a few hundred serial round trips the page waited out.

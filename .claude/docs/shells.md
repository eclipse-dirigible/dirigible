### Application shell (`resources-application`) — the pure-Harmonia app launchpad

`components/resources/resources-application` (`dirigible-components-resources-application`), served at **`/services/web/application/`**, is the shell **for the application layer** — the IDE stays AngularJS + BlimpKit, but the app layer is pure Java + Harmonia (the AngularJS Dashboard shell it replaced, `resources-dashboard`, was removed in #6589). It reuses the shared runtime for the built-in Dashboard/Inbox/Documents/Reports pages (Pinecone routes into `#app`) and aggregates the **`application-perspectives`** extension point for the domain apps, hosting each one's generated SPA in an embedded iframe (`?embedded`). It shows **named perspective groups only**, so the platform's AngularJS *utility* perspectives (e.g. `platformSettings` → `/services/web/perspective-settings/settings.html`, `ng-app="settings"`) are excluded — **never iframe an AngularJS perspective into the Harmonia shell, it won't bootstrap standalone**. Each generated app contributes one per-entity perspective to `application-perspectives` whose `groupId` is the intent entity's `group:`; the groups are defined once in a dedicated navigation-groups project (the codbex pattern). Wired into `components/pom.xml` (modules + dependencyManagement) and `group-ui`.

**A perspective the aggregator cannot place is never dropped, and never silently** (issue [#6646](https://github.com/eclipse-dirigible/dirigible/issues/6646)). `platform-core/extension-services/modules/perspectives.mjs` pushes perspectives into groups **by `groupId`**; an id matching no group used to be discarded, so the group rendered empty — indistinguishable from "no module contributes here", with no console warning and no log line anywhere (the *authored-but-silently-unconsumed* class). Now: the unmatched id is `console.error`-ed naming the perspective and the id, then placed in the extension point's **default group** — a group declaring `isDefault: true` — else the platform's `undefined-group` catch-all, else handed back standalone for the shell to render. The **single-group shells** (`resources-personal` / `resources-partner` / `resources-admin`) declare their one group `isDefault: true`, so their generated perspectives (`ui/{my,partner,admin}/*-perspective.js.template`) deliberately declare **no `groupId` at all** — repeating a platform constant in every generated artifact is a coupling that can only drift, and the "My Work" → "Personal" rename proved it: every already-generated module kept `groupId: 'my'` and its personal pages vanished. `undefined-group` is deliberately **not** marked default, so a no-`groupId` perspective on `application-perspectives` still comes back standalone and the shells' catch-all "Other" section renders it (that branch now rescues **any** `kind`, not just `PRIMARY` — enumerating kinds is how `PERSONAL` fell off the end of the chain). `PerspectiveGroupAggregationIT` guards both placements; `IntentEmissionCoverageIT` asserts the perspective is **inside** its group, not merely present in the response.

### Builder shell (`resources-builder`) — the conversational AI intent builder

`components/resources/resources-builder`, served at **`/services/web/builder/`** (shell id `builder`, `.access`-gated to ADMINISTRATOR/DEVELOPER), is a standalone Harmonia shell where you **describe an application in plain language and publish it**. It adds **no backend**: it is a frontend orchestration over endpoints that already ship, reusing the shared `application-core` runtime (theme/notifications/branding/i18n) by absolute URL. One screen, so there is deliberately **no Pinecone router**.

The loop: chat → `POST /services/ide/intent/agent` → **re-validate the proposal client-side through `POST /parse`** → auto-apply (no diff/Accept — the chat text is the narration) → the canvas redraws. **The agent answers 200 even when its proposal still fails validation** (the server's two repair rounds were exhausted, signalled only as trailing prose in `reply`), so the client-side re-validation is load-bearing, not belt-and-braces — an invalid proposal is shown as issues and never reaches the buffer. Project and file management are hidden: the project id is a slug of the intent's `name`, created lazily on the first accepted proposal and never renamed; every accepted proposal is auto-saved, so a reload restores from disk. Chat history is persisted **server-side** per `(tenant, project, surface)` and restored on open (the agent endpoint is stateless, so the transcript is a record the platform keeps, not browser state); the store appends one turn at a time and a failed append is carried by the next turn rather than breaking the chat.

**The one button** (`js/services/pipeline.js`, the `publish` store) runs save → **Problems baseline** → `/intent/generate` (which generates the models AND the code from them in that one call, reporting each recipe's outcome in `codeGenerations`) → publisher → healthcheck poll + **Problems diff filtered to `/<project>`**. That diff is the only honest "published clean" signal — publishing is synchronous but reports nothing about what the synchronizers made of the artefacts, so a client-Java compile error or a failed CSVIM seed surfaces there and nowhere else. The success panel's "try it here" links are **discovered** (`platform-shells`, plus the app's own perspective path from `application-perspectives`) — never assembled from a guessed `gen/<model>` convention, which would 404 the moment a template changed its layout.

Gotchas this shell paid for (all confirmed by `IntentBuilderShellIT`):
- **Never put an Alpine binding on `<i x-h-lucide>`.** The plugin REPLACES the `<i>` with the rendered svg, so a binding would be lost — it throws instead, and the uncaught throw **aborts Alpine's walk over everything below it** (the toolbar rendered, the whole split pane did not). Use an `<svg x-h-lucide>` placeholder for any `:data-lucide` / `:class` / `x-show`.
- **The idempotent creates answer `304`, and `response.ok` is 2xx-only.** `POST /workspaces/{ws}` and `.../{ws}/{project}` return 201 the first time and **304 NOT MODIFIED** afterwards, so a naive `!response.ok` throw makes the *second* save fail while the first succeeded. The fetch helper takes an `alsoOk: [304]`.
- **The workspace may not exist at all** on an instance where the user never opened the IDE; creating a project inside a missing workspace answers 404, so `ensureProject` creates the workspace first.
- The agent endpoint can make three upstream calls at 120s each — the client timeout is **7 minutes**, with a staged typing indicator.
- **Ask `GET /services/ide/intent/agent/status` whether the assistant is usable, never a throwaway `/agent` turn.** The shell probes on load so an unconfigured instance says so before the user types; the status endpoint reads configuration only, so it costs no upstream model call (a probe that posted a real turn would burn an Anthropic round-trip on every page load of a *working* instance).

The mxGraph rendering is **shared, not copied**: `editor-intent/js/intent-diagrams.js` exposes the framework-free `window.IntentDiagrams.render(model, host)` / `.dispose(host)`, extracted from the Intent Editor's controller and loaded by both (the shell by absolute URL). A standalone page must link **`platform-core/ui/styles/fonts.css`** or the glue cards' SAP-icon glyphs render as tofu. Tests: `IntentBuilderShellIT` — a `@Tag("smoke")` bootstrap check plus the full journey against a **local HTTP stub of the Anthropic upstream** (`DIRIGIBLE_INTENT_AI_BASE_URL`, the same override `IntentAgentServiceTest` uses in-process), so it needs no key and no network.

### Monitoring shell (`resources-monitoring`) — the operations surface

`components/resources/resources-monitoring`, served at **`/services/web/monitoring/`** (shell id `monitoringShell`, order 37, icon `activity`, gated to ADMINISTRATOR/OPERATOR/DEVELOPER by `monitoring.access`), answers "is the system healthy, and if not, what broke?" without opening the IDE. Same skeleton as `resources-my` / `resources-admin`: a pure-resources module over the **shared** runtime at `/services/web/application-core/shell/`, **no new backend** — every page reads an existing, role-gated platform endpoint. Six pages: **Overview** (health, readiness, artefacts in error, failed jobs, process incidents, DB-pool pressure, broker backlog — polled every 30 s, pausable), **Processes** (instances + the live BPMN diagram + the two triage actions, retry/skip), **Jobs** (list, execution log with the tenant column, enable/disable/trigger), **Logs** (the `/websockets/ide/console` live stream + the log files), **Messaging** (read-only), **System** (the build this instance runs + the JVM snapshot + session-local sparklines). Design docs: repo-root `MONITORING_SHELL_PLAN.md`; delivered on PRs [#6613](https://github.com/eclipse-dirigible/dirigible/pull/6613) (backend prerequisites), [#6614](https://github.com/eclipse-dirigible/dirigible/pull/6614) (shell + Overview) and [#6615](https://github.com/eclipse-dirigible/dirigible/pull/6615) (the remaining pages).

Things worth knowing before changing it:

- **The scope line is deliberate.** Deep and destructive tooling — SQL console, terminal, message purging, process-variable editing, tracing, **log-level changes** — stays in the Workbench permanently; each page links there instead of cloning it. Re-implementing a BPMN modeler or a data grid here means we overshot.
- **Two backend prerequisites shipped with it** (#6613): `HttpSecurityURIConfigurator` now carries a **monitoring gate** (`/services/bpm/bpm-processes/**`, `/services/ide/{monitoring,logs,loggers,messaging-monitoring}/**`, `/websockets/ide/console`) matched **before** the DEVELOPER gate, aligning the URL layer with those controllers' declared `@RolesAllowed` — the rest of `/services/ide/**` and `/services/bpm/**` (workspaces, git, publisher, the BPMN modeler) stays DEVELOPER-only, and `HttpSecurityURIConfiguratorTest` guards the whole matrix including the ordering. And `GET /services/core/artefacts` (`ArtefactStatusEndpoint` in `core-base`) aggregates the `ArtefactService` beans — every synchronizer registers one, so the bean list *is* the inventory; it replaces depending on the IDE perspective's `artefacts.mjs` JS aggregator.
- **Every read goes through `js/services/ops.js`**, and the aggregate pages wrap each source in `ops.soft(...)` so one unavailable engine degrades to a marked tile instead of an empty screen. The Overview's incident scan is one request per active instance (there is no bulk endpoint) and is capped at 50 — the page says so rather than silently reporting "no incidents".
- **The BPMN diagram is the same visualizer the IDE uses** (`bpmn-visualization` webjar), loaded on first use (~1 MB — the Overview must not pay for it) and themed through Harmonia's own `--foreground` / `--input-background` / `--positive` / `--negative` variables. The server-side PNG endpoint stays a fallback: it is static and theme-blind.
- **Known data issues, filed but not blocking:** job logs leak and clear across tenants ([#6606](https://github.com/eclipse-dirigible/dirigible/issues/6606)), tracing reads/deletes are cross-tenant ([#6607](https://github.com/eclipse-dirigible/dirigible/issues/6607)), `TracingFacade.disableTracing()` sets the flag to `"true"` ([#6608](https://github.com/eclipse-dirigible/dirigible/issues/6608)), `JobEndpoint.emailremove` is doubly broken ([#6609](https://github.com/eclipse-dirigible/dirigible/issues/6609)). v1 is an instance-level operator surface and shows the job-log tenant column until #6606 lands. The BPM/Flowable queries **are** tenant-filtered — no issue there.
- **"Which build is this?" is answered from `/services/core/version`** — the same payload the Workbench's About window reads, in the `version` store (read once; a running instance never changes its build), rendered as the System page's **Build** card and condensed onto the sidebar footer, where every page shows it. The keys behind it (`DIRIGIBLE_PRODUCT_NAME` / `_VERSION` / `_COMMIT_ID`) ship **unfiltered** in `dirigible-commons.properties`, so until `build/application/src/main/resources/dirigible.properties` re-declared them (that module filters its resources and runs the git-commit-id plugin) every stock instance reported the literal `${project.version}` and the About window hid the row. A downstream distribution overrides the same three keys with its own `dirigible.properties`; the UI treats a value that still looks like a Maven placeholder as unknown.
- **`MonitoringShellIT`** (`@Tag("ui")`) is the guard that matters: the Alpine-bootstrap failure mode (an Alpine binding on an `<i x-h-lucide>` aborts the walk) has no DOM or server-side symptom, so only a real browser catches it. Each page root carries a stable id (`monitoring-<page>-page`) so the assertions do not depend on what happens to be deployed.

## Messaging perspective (`ide-messaging-monitoring` + `perspective-messaging`)

A devops/debug surface for the embedded ActiveMQ broker — **embedded mode only**, see the broker-mode note below. Three modules cooperate:

- **`components/ide/ide-messaging-monitoring`** — backend service + REST endpoint. Constructor-injects the `BrokerService` bean from `engine-listeners` (the broker is started with `useJmx=false` in `EmbeddedBrokerMessagingConfig`, so JMX is unavailable — read state directly off the bean instead). Both the service and the endpoint are `@Conditional(EmbeddedMessagingBrokerCondition.class)` — **with an external broker there is no `BrokerService` bean, so neither is registered and every endpoint here answers 404** (an external broker is administered from its own console). `RegionBroker.getDestinationMap()` enumerates queues and topics; `Destination.getDestinationStatistics()` exposes the counters; `Destination.browse()` returns the in-memory pending set without consuming. Endpoints live under `/services/ide/messaging-monitoring/` with `@RolesAllowed({ADMINISTRATOR, DEVELOPER, OPERATOR})`:
  - `GET /summary` — broker meta + every queue/topic with counters
  - `GET /queues/{name}/messages?limit=N` — non-destructive browse (capped at 200 by default, body preview at 64 KB)
  - `DELETE /queues/{name}/messages` — purge
  - `DELETE /queues/{name}/messages/{messageId}` — remove a single message
  - `DELETE /queues/{name}` and `DELETE /topics/{name}` — remove the destination (returns 409 if consumers are still attached — `IllegalStateException` translated by the endpoint)
- **`components/ui/perspective-messaging`** — perspective shell (id `messaging`, order 1010), icon, menu, extensions.
- **`components/ui/view-messaging-destinations`** (left) and **`components/ui/view-messaging-browser`** (center) — filterable list of destinations and master-detail message inspector. They communicate over `MessageHub` topics `messaging.destination.selected` (selection broadcast), `messaging.destination.selection.request` (browser asks destinations view to re-broadcast on init — fixes the iframe-startup race), and `messaging.broker.refresh` (browser asks destinations view to re-poll after a mutating action). Confirm-dialogs go through `DialogHub.showAlert({type:'confirmation', buttons:[...]})`.

**Topic limitation:** JMS topics do not retain non-persistent messages, so the browser shows live counters but no message list for topics. Message-body decoding prefers `ActiveMQTextMessage.getText()`; for `BytesMessage`-style payloads, the first 64 KB are inspected and rendered as UTF-8 when they look textual, otherwise base64-encoded.

**Broker mode — embedded or external** (`engine-listeners/.../listeners/config/`). Set `DIRIGIBLE_MESSAGING_BROKER_URL` (plus optional `DIRIGIBLE_MESSAGING_BROKER_USERNAME` / `_PASSWORD`) and the platform stops starting its own broker and connects to that one instead — `tcp://`, `ssl://`, `failover:(…)`, e.g. Amazon MQ or a dockerized ActiveMQ shared by several deployments. Unset (or blank) keeps the previous behaviour exactly: an in-process `BrokerService` reached over `vm://localhost`.

The two modes are two `@Configuration` classes — `EmbeddedBrokerMessagingConfig` and `ExternalBrokerMessagingConfig` — selected by `EmbeddedMessagingBrokerCondition` / `ExternalMessagingBrokerCondition`, which are the exact negation of one another, so exactly one always applies. Three things are worth knowing before touching this:

- **The conditions read `DirigibleConfig`, not the Spring `Environment`** — deliberately, and this is the repo's only hand-written `Condition`. Dirigible resolves a key across its own layers and a value placed there programmatically (`Configuration.set`, which is how `ExternalMessagingBrokerIT` selects the mode) never reaches the `Environment`, so `@ConditionalOnProperty` would not see it. Conditions evaluate once per context refresh: an integration test must set the config in a static `@BeforeAll`, before the context is created.
- **Both modes define the `ActiveMQConnection` and `ActiveMQSession` beans**; only the embedded one defines `ActiveMQBroker`. Nothing else changes, because every consumer — the `.listener` artifacts, the client-Java listeners (`engine-java`'s `ListenerClassConsumer`), `MessagingFacade` — reaches the broker through `ActiveMQConnectionArtifactsFactory`, which resolves the `ActiveMQConnectionFactory` **by type**. Swapping that one bean is the whole change; do not reintroduce a `@DependsOn("ActiveMQBroker")` outside the embedded config.
- `DIRIGIBLE_MESSAGING_USE_DEFAULT_DATABASE` configures the embedded broker's persistence only and is logged as ignored in external mode. Anything else that reaches for the `BrokerService` bean must tolerate its absence (`ObjectProvider`, as `CloseActiveMQResourcesApplicationListener` does) or be conditional on the embedded mode (as the monitoring component is). An unreachable external broker fails startup on purpose.
- **A client-id connection is never reconnected by the transport** (#7851). The client-Java topic listeners subscribe durably, so their connections carry a stable client id (`ListenerClassConsumer.durableSubscriptionId`). Over a `failover:` URL, `FailoverTransport` used to reconnect such a connection by itself and replay the client id while the broker still held the previous, half-open socket - refused ("already connected"), reconnected at once, refused again: a loop that, every subscription at once, outlived a rolling deploy by 40 minutes on a small broker. `ActiveMQConnectionArtifactsFactory.createConnection(listener, clientId)` therefore sets the transport's `maxReconnectAttempts` to 0 after `start()` (not before - it would also cap the first connect), the loss reaches the exception listener, and `ListenerClassConsumer` takes the tenant's (or the global) subscriptions out of its registration; the next reconciliation pass closes the dead connections and subscribes the scope again, paced, while the durable subscription keeps its messages. Anonymous (queue) connections keep `FailoverTransport`'s reconnect. Keep it that way for any new client-id connection. **And a connection that fails to start is closed inside the factory** (#7853): the caller never receives it, so a refused `start()` (another instance still holds the client id - the rolling-deploy overlap) used to leak a connection whose started transport, at its default unlimited reconnect, replayed the id after the next interruption and was refused against its own instance's later subscription, thousands of times a minute. `createConnection` closes it on any failure before rethrowing; never let a created connection escape a failed attempt.
- **A scope's subscriptions share one connection** (#7875, `DIRIGIBLE_MESSAGING_LISTENER_CONNECTIONS=shared`, the default; `per-listener` is the shape before). The connection is what a broker meters - Amazon MQ's `mq.t3.micro` admits 300, each costs broker heap - and one per subscription per tenant put a generated suite of ~130 handlers at `130 x (tenants + 1)`. `ListenerConnectionMode` (a bean, read once at boot, refused by name on an unknown value) is consumed by both subscribing sides: `ListenerClassConsumer` opens one client-id connection per tenant (`dirigible-java-tenant-<id>`) plus one for the global destinations (`dirigible-java-global`), each subscription a session on it, the durable subscriptions told apart by their names (still handler + physical destination); `SharedListenerConnection` is the one anonymous connection every `.listener` artefact's session rides, fanning a broker error out to every attached artefact's `onError`, replaced by the next attach once dead, closed by `ListenersManager.stopListeners`. The loss of a shared client-id connection is the loss of its whole scope - the unit #7851 already re-subscribes - and `ListenerClassConsumer.shutdown` (`@PreDestroy`) closes everything so the client ids are released at once for the instance that replaces this one. The durable identity differs between the modes (client id = subscription id before, client id = scope now), so switching an existing deployment used to leave the previous mode's durable subscriptions offline, retaining every message, until the broker's `offlineDurableSubscriberTimeout` (7 days embedded, never on a default external ActiveMQ). Since #7890 a scope that subscribes queues the other mode's identity of each of its durable subscriptions, and `ListenerClassConsumer.reconcile` unsubscribes them on the reconciliation thread, one client id (one connection) at a time; "no durable subscription exists" counts as done, a client id still held (the previous instance of a rolling deploy) is refused and retried on the next pass, and what is done is remembered for the life of the process - so every boot pays one short connection per topic handler per tenant in the shared mode (one per scope in `per-listener`), and nothing afterwards. `ListenerSubscriptionReclaimIT` pins it against the embedded broker's `TopicRegion`. `ListenerConnectionSharingIT` asserts the broker's own connection count for N handlers x M tenants. **The shared client ids carry the deployment's identity** (#8655): `DIRIGIBLE_MESSAGING_CLIENT_ID_PREFIX`, else `DIRIGIBLE_APP_ID`, makes them `dirigible-java-<prefix>-tenant-<id>` / `dirigible-java-<prefix>-global`. A client id is unique per broker and every application has a `default-tenant`, so two applications on one broker used to claim the same ids and the second was refused for as long as the first ran - its listeners in that scope never subscribed, with one WARN at boot and a DEBUG per retry. With neither key set the ids stay unprefixed (one application per broker). With a prefix the unprefixed identities are queued for reclaim like a mode switch's (the names are this deployment's own, so another application's subscriptions are never touched), and a shared connection refused by `InvalidClientIDException` is reported at WARN every 10 minutes while it lasts, naming the key. `ListenerClientIdPrefixIT` holds a tenant's unprefixed id and proves the tenant's handler still subscribes.


**The redelivery budget is configuration** (#8745). `ActiveMQConnectionArtifactsFactory.configureRedeliveryPolicy`, which every listener path applies per subscription, reads `DIRIGIBLE_MESSAGING_REDELIVERY_INITIAL_DELAY_MILLIS` (1000), `_BACK_OFF_MULTIPLIER` (5, a decimal, `1` = fixed interval), `_MAXIMUM_DELAY_MILLIS` (-1 = no cap) and `_MAXIMUM_REDELIVERIES` (3, `-1` = unlimited) each time a subscription opens; the defaults are the budget it always had - redeliveries about 1, 6 and 31 s after the first delivery, then `ActiveMQ.DLQ`. ActiveMQ computes the delays client side (initial, then previous x multiplier, capped), so the plain `redeliveryDelay` is kept equal to the initial delay - it is used only when there is no previous delay to multiply. An invalid value is logged at WARN and replaced by its default. While a message waits for its redelivery the consumer is stopped, so a long delay pauses that subscription's other messages too. `RedeliveryPolicyConfigurationTest` pins the delay sequence.

**Shared message store — the embedded broker in a rolling deployment.** `DIRIGIBLE_MESSAGING_USE_DEFAULT_DATABASE=true` (the default) puts the queued messages in the SystemDB, which every instance of the deployment shares — and a shared store admits exactly one broker at a time. Getting that arbitration wrong deadlocked make-before-break rollouts on ECS/Kubernetes ([#7002](https://github.com/eclipse-dirigible/dirigible/issues/7002)), so `EmbeddedBrokerMessagingConfig` now configures three things around it:

- **The start does not run on the context thread** (`BrokerService#setStartAsync(true)`, shared store only). Taking the store means waiting for whoever holds it to let go, which during a rollout is until the orchestrator stops the previous instance — and it will not stop it until the new one reports ready. Starting synchronously therefore closed a circle: `/actuator/health/readiness` never flipped, the deployment circuit breaker killed the task, every retry inherited the wait. `awaitSharedStore` still gives the start a 5 s grace so an uncontended instance comes up with messaging already attached, and logs one WARN when it is genuinely waiting; a real start failure (an unusable database) still aborts the context refresh, as before.
- **The store is claimed with a `LeaseDatabaseLocker`, not ActiveMQ's default row lock.** The default holds `SELECT … FOR UPDATE` for as long as the holder's connection lives, so a killed instance keeps the store until the database notices a dead peer. A lease expires on a clock: 30 s, renewed every 10 s. Two consequences to keep in mind — the **lease holder id must identify the instance** (`hostname:pid`), because renew and release are keyed by it and every instance names its broker `localhost`; and `maxAllowableDiffFromDBTime` is set so the lease is measured against the **database's** clock, or a fast instance declares a living master expired. A graceful stop releases the lease immediately; a lease that could not be released (an in-process H2 closed by its own JVM shutdown hook before the broker stopped) just costs the next boot up to 30 s of waiting, with the instance up and serving throughout.
- **The JMS connection and session attach on first use** (`@Lazy` on both beans in the embedded config, and on every injection point that takes them — `MessageProducer`, `MessageConsumer`, `CloseActiveMQResourcesApplicationListener`). There is nothing to connect to until the broker holds the store, so an eager connection would put the deadlock straight back into bean creation. A send or a listener that runs before mastery fails and is retried (the listener synchronizer's START phase retries every pass); the shutdown listener asks the bean factory whether the connection was ever resolved rather than opening one just to close it. The external mode stays **eager** on purpose — an unreachable external broker is a misconfiguration and must fail the startup.

The `doCreateTables` "already exists" WARN storm with full stack traces on every boot after the first was the same feature's diagnostic papercut: ActiveMQ decides whether those failures deserve a warning by probing `DatabaseMetaData` for its own, upper case table name, which never matches on a database that folds unquoted identifiers to lower case. `alignSchemaCaseWithDatabase` renames the adapter's tables to the case the database reports, so the probe finds them and the failures drop to DEBUG — the DDL still runs, so an ActiveMQ upgrade that alters the schema is unaffected.

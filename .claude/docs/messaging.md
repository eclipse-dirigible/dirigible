## Messaging perspective (`ide-messaging-monitoring` + `perspective-messaging`)

A devops/debug surface for the embedded ActiveMQ broker — **embedded mode only**, see the broker-mode note below. Three modules cooperate:

- **`components/ide/ide-messaging-monitoring`** — backend service + REST endpoint. Constructor-injects the `BrokerService` bean from `engine-listeners` (the broker is started with `useJmx=false` in `EmbeddedBrokerMessagingConfig`, so JMX is unavailable — read state directly off the bean instead). Both the service and the endpoint are `@Conditional(EmbeddedMessagingBrokerCondition.class)` — **with an external broker there is no `BrokerService` bean, so neither is registered and every endpoint here answers 404** (an external broker is administered from its own console). `RegionBroker.getDestinationMap()` enumerates queues and topics; `Destination.getDestinationStatistics()` exposes the counters; `Destination.browse()` returns the in-memory pending set without consuming. Endpoints live under `/services/ide/messaging-monitoring/` with `@RolesAllowed({ADMINISTRATOR, DEVELOPER, OPERATOR})`:
  - `GET /summary` — broker meta + every queue/topic with counters
  - `GET /queues/{name}/messages?limit=N` — non-destructive browse (capped at 200 by default, body preview at 64 KB)
  - `DELETE /queues/{name}/messages` — purge
  - `DELETE /queues/{name}/messages/{messageId}` — remove a single message
  - `DELETE /queues/{name}` and `DELETE /topics/{name}` — remove the destination (returns 409 if consumers are still attached — `IllegalStateException` translated by the endpoint)
- **`components/ui/perspective-messaging`** — perspective shell (id `messaging`, order 1010), icon, menu, extensions.
- **`components/ui/view-messaging-destinations`** (left) and **`components/ui/view-messaging-browser`** (center) — filterable list of destinations and master-detail message inspector. They communicate over `MessageHub` topics `messaging.destination.selected` (selection broadcast), `messaging.destination.selection.request` (browser asks destinations view to re-broadcast on init — fixes the iframe-startup race), and `messaging.broker.refresh` (browser asks destinations view to re-poll after a mutating action). Confirm-dialogs go through `DialogHub.showAlert({type:'confirmation', buttons:[...]})`.

**Topic limitation:** JMS topics do not retain non-persistent messages, so the browser shows live counters but no message list for topics. Message-body decoding prefers `ActiveMQTextMessage.getText()`; for `BytesMessage`-style payloads, the first 64 KB are inspected and rendered as UTF-8 when they look textual, otherwise base64-encoded.

**Broker mode — embedded or external** (`engine-listeners/.../listeners/config/`). Set `DIRIGIBLE_MESSAGING_BROKER_URL` (plus optional `DIRIGIBLE_MESSAGING_BROKER_USERNAME` / `_PASSWORD`) and the platform stops starting its own broker and connects to that one instead — `tcp://`, `ssl://`, `failover:(…)`, e.g. Amazon MQ or a dockerized ActiveMQ shared by several deployments. Unset (or blank) keeps the previous behaviour exactly: an in-process `BrokerService` reached over `vm://localhost`.

The two modes are two `@Configuration` classes — `EmbeddedBrokerMessagingConfig` and `ExternalBrokerMessagingConfig` — selected by `EmbeddedMessagingBrokerCondition` / `ExternalMessagingBrokerCondition`, which are the exact negation of one another, so exactly one always applies. Three things are worth knowing before touching this:

- **The conditions read `DirigibleConfig`, not the Spring `Environment`** — deliberately, and this is the repo's only hand-written `Condition`. Dirigible resolves a key across its own layers and a value placed there programmatically (`Configuration.set`, which is how `ExternalMessagingBrokerIT` selects the mode) never reaches the `Environment`, so `@ConditionalOnProperty` would not see it. Conditions evaluate once per context refresh: an integration test must set the config in a static `@BeforeAll`, before the context is created.
- **Both modes define the `ActiveMQConnection` and `ActiveMQSession` beans**; only the embedded one defines `ActiveMQBroker`. Nothing else changes, because every consumer — the `.listener` artifacts, the client-Java listeners (`engine-java`'s `ListenerClassConsumer`), `MessagingFacade` — reaches the broker through `ActiveMQConnectionArtifactsFactory`, which resolves the `ActiveMQConnectionFactory` **by type**. Swapping that one bean is the whole change; do not reintroduce a `@DependsOn("ActiveMQBroker")` outside the embedded config.
- `DIRIGIBLE_MESSAGING_USE_DEFAULT_DATABASE` configures the embedded broker's persistence only and is logged as ignored in external mode. Anything else that reaches for the `BrokerService` bean must tolerate its absence (`ObjectProvider`, as `CloseActiveMQResourcesApplicationListener` does) or be conditional on the embedded mode (as the monitoring component is). An unreachable external broker fails startup on purpose.

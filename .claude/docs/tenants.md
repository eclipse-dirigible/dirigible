## Tenant resolution strategy (`core-tenants` + `core-base`)

How the current tenant of a request is determined is configurable through `DIRIGIBLE_TENANT_RESOLUTION_STRATEGY` (`TenantResolutionStrategy` in `core-base`, read once per `TenantExtractor` instance, i.e. at context refresh):

- **`SUBDOMAIN`** (default, unchanged behaviour) — the subdomain of the `host` / `x-forwarded-host` header is matched against `DIRIGIBLE_TENANT_SUBDOMAIN_REGEX` and looked up by subdomain. A host naming no registered tenant is answered with the 404 written by `TenantContextInitFilter`. Every tenant needs its own host.
- **`TOKEN_GROUPS`** — the tenant is the one the user selected, read from the HTTP session attribute `TenantSelectionConstants.SELECTED_TENANT_ID_SESSION_ATTRIBUTE` and required to be `PROVISIONED`. The host is never consulted, so one host serves every tenant. No session, no selection, an unknown selection, or a tenant that is not provisioned yet all fall back to the **default tenant** — machine-to-machine calls and anonymous requests carry no session, and a stale selection must not lock a user out.

`TOKEN_GROUPS` exists for deployments where authorization is carried in identity provider groups named **`<tenantId>.<appId>.<role>`** (e.g. `acme.library.Owner`). `TenantGroupsParser` (`core-base`, `base/tenant/groups/`, free of Spring/servlet/OAuth2 types) turns a user's groups into `UserTenantAssignments`: groups of this deployment's application (`DIRIGIBLE_APP_ID`) become that tenant's roles, groups of other applications are ignored, and non-tenant-bearing groups (plain `DEVELOPER`, `OPERATOR`) stay global roles. The role part may contain dots; tenant and application ids may not. The groups claim is `DIRIGIBLE_TENANT_GROUPS_CLAIM` (`cognito:groups` by default, `groups` on Keycloak realms) — **set it explicitly on a Keycloak realm**: it is the one place both the login mapping and the selection read, so a wrong claim silently means "no tenants".

## Tenant selection (`security-oauth2`, both OIDC profiles)

What writes the session attribute — the identity-provider half of `TOKEN_GROUPS`. It lives in `security-oauth2` (`.../oauth2/tenant/`) rather than in a profile module, because Cognito and Keycloak need the same thing and their configurations differ only in the groups claim. Everything here is gated on the strategy, not on a Spring profile, so it is inert in `SUBDOMAIN` mode.

- **`TenantAwareAuthoritiesMapper`** behind each profile's `userAuthoritiesMapper()`: in `SUBDOMAIN` mode every group of the provider's own claim becomes an authority (byte-identical to what the two profiles did inline before); in `TOKEN_GROUPS` mode only `globalRoles()`, since which tenant's roles apply is unknown at login.
- **`TenantSelectionManager`**: `selectTenant` validates the tenant against the user's **own groups** (403 if not a member) and requires it `PROVISIONED` here (409), writes the session attribute and rebuilds the `OAuth2AuthenticationToken` with `globalRoles ∪ rolesFor(tenant)`, saved through the `SecurityContextRepository` — the `OAuth2SessionRevalidationFilter.refreshAuthentication` sequence, without rotating the session id. `ensureConsistent` re-applies them when they drift and **drops a selection whose group was revoked** or whose tenant is now **suspended**. The 409 carries one of three reasons, each a state of the tenant: `NOT_PROVISIONED_HERE` (ends by waiting), `UNKNOWN_HERE` (never ends by itself), `SUSPENDED` (ends only when the provisioner resumes the tenant, see "Suspending a tenant") - the same for `selectTenant`, `enterTenant` (bearer) and `enterTenantAsClient`. The suspended check in `ensureConsistent` reads the registry only when the request does not already run in the selected tenant: `TenantExtractor` resolves a provisioned selection only (its cached lookup), so a working session pays no query.
- **`TenantSelectionEndpoint`** at `services/security/tenant-selection`: `GET` lists `{selectedTenantId, tenants:[{id,name,provisionedHere}]}`, `POST {tenantId}` enters one and doubles as the switch. No `@RolesAllowed` on purpose — a user who has not picked yet has only global roles, and a single-tenant user none at all. JSON-only body is the CSRF defence (the chains disable CSRF tokens), as in `NativeLoginEndpoint`.
- **`TenantSelectionFilter`**: one tenant → auto-select (refused because it is suspended: a browser goes to the picker, a JSON caller gets `409 {reason: "SUSPENDED", …}`); several → `302 /tenant-selection.html` for a browser, `409 {"error":"TENANT_SELECTION_REQUIRED","tenants":[…]}` otherwise; none → pass for holders of a known global role (`Roles` or a registered `.roles` role, `KnownGlobalRoles`), else 302 to the picker for a browser / 403 `NO_TENANT_ASSIGNED` JSON otherwise (#7839). Every group not naming a tenant still parses to a global role and an authority, so an unrelated group (Cognito's `<userPoolId>_<providerName>` federation group, another system's group in a shared pool) used to be enough to serve the default tenant's shell to a user who could do nothing in it; the picker's empty state now reads "No access to this application". Non-`OAuth2AuthenticationToken` requests (M2M bearer, anonymous, basic) pass through.
- **Registration** is `TenantSelectionSecurityConfigurator`, the repo's **first `CustomSecurityConfigurator`**. `HttpSecurityURIConfigurator.configure` applies those before its own matchers and every chain calls it, so one bean adds the filter `before AuthorizationFilter` (it must precede authorization, or a user without a tenant is 403'd before reaching the picker) and claims `/tenant-selection.html` as `authenticated()` — no per-profile wiring, no edit to the static URL matrix.
- **The picker** is `security-oauth2/src/main/resources/static/tenant-selection.html` — Harmonia + Alpine, the load order of the Home landing page, inline script, `?switch=true` to change tenant. A classpath static page because the registry is itself tenant-scoped. A tenant is a tile per `TenantOption.State`: `READY` can be pressed; `PREPARING`, `SUSPENDED` (greyed, a "Suspended" badge and "This tenant is suspended. Contact its owner.") and `UNKNOWN` cannot, each with its own sentence.
- **The tenant chip** (#7459) is how a page shows which tenant it runs in and switches it in place - the only other way to switch is the picker's `?switch=true`, which no page links to. `CurrentTenantEndpoint` at `GET services/security/tenant-selection/current` answers on **every** strategy (unlike the selection endpoint, which is 404 outside `TOKEN_GROUPS`): `{tenant:{id,name,defaultTenant}, multitenant, resolutionStrategy, switchable, tenants:[TenantOption]}`. `tenant` is `TenantContext.getCurrentTenant()`; `tenants` is `availableTenants` **only** for an `OAuth2AuthenticationToken` under `TOKEN_GROUPS` (a bearer request names its tenant per request, and under `SUBDOMAIN` the groups say nothing - asking would also raise the manager's unknown-tenant WARN on every page load); `switchable` means a `READY` option other than the current one exists. No `@RolesAllowed`, same reasoning as the selection endpoint. Its path is deliberately **under** the selection endpoint's so `UNFILTERED_PREFIXES` covers it by `startsWith`: a user who has not chosen yet is told they are in the default tenant, not answered with the filter's 409 (`TenantSelectionFilterTest` pins it). The frontends: the Harmonia shells' shared `tenant` store + fragment (see the Harmonia notes), and for the Workbench `platform-core/ui/platform/tenant.js` (`platformTenant` module, bundled in `ng-shell`) rendered by `header.html` next to the avatar. `TenantWidgetIT` / `TenantWidgetSingleTenantIT` drive the three mount styles in a browser; `TenantSelectionIT` and the two `*MultitenantModeIT`s pin the payload per strategy.
- **A bearer request has no session, so it names its tenant per request** (#7446): the `X-Tenant-Id` header (`TenantSelectionConstants.TENANT_HEADER`). `TenantExtractor` still opens every bearer request in the default tenant (it runs before authentication and can validate nothing); `TenantSelectionFilter`'s `JwtAuthenticationToken` branch then calls `TenantSelectionManager.enterTenant` — the same membership/provisioned checks as `selectTenant`, nothing stored — replaces the `SecurityContextHolder` authentication with one carrying the token's authorities plus the tenant roles, and re-enters `tenantContext.execute(tenant, …)` for the rest of the chain. A refusal answers the endpoint's `{reason, message}` JSON with `Reason.httpStatus()` (403 / 409). Without the header: default tenant with the global roles; an ID token whose groups grant no known global role is refused 403 there (the converter no longer refuses it — it cannot see the request), an access token passes untouched. `X-Tenant-Id` is in the default `DIRIGIBLE_CORS_ALLOWED_HEADERS`. Covered end-to-end by `ExternalFrontendTenantSelectionIT`.
- ⚠ **The re-scope holds only while `TenantContextInitFilter` runs ahead of `TenantSelectionFilter` in the same security chain.** Every profile's chain adds it explicitly (`addFilterBefore(tenantContextInitFilter, OAuth2LoginAuthenticationFilter.class)` on the OIDC profiles). A chain that does not leaves it to the servlet filter Spring Boot registers for the `@Component`, which has the lowest precedence and runs **after** the whole security chain: it re-opens every bearer request in the default tenant over the tenant the selection entered, so the request is served from the default tenant with the roles of the tenant it named. Until #8458, `cognito` and `github` were built that way, and the tenant selection ITs, which run on `keycloak`, could not see it. `TenantSelectionChainValidator` (`security-oauth2`) now refuses to start on such a chain, and `CognitoBearerTenantIT` runs the `cognito` profile against the mock identity provider with Cognito-shaped tokens (`token_use`, `client_id`, `cognito:groups`).

⚠ In `TOKEN_GROUPS` mode the authorities of a session are **recomputed from the groups**, so a platform role such as `ADMINISTRATOR` must be granted as a *global group*; anything granted another way is dropped on the next request. Note also that a fresh selection applies from the **next** request: the tenant scope of the current one was opened before the selection was written, which is why the picker navigates away on success.

`TenantResolutionConfigValidator` (`core-tenants`) refuses to start on an unusable combination: with `TOKEN_GROUPS` the app id must be set and dot-free, `DIRIGIBLE_MULTI_TENANT_MODE` must be true, the groups claim non-blank, and `DIRIGIBLE_MULTI_TENANT_MODE_COGNITO_SINGLE_USER_POOL` (the legacy `custom:tenant` model of `CognitoTenantFilter` / `KeycloakTenantFilter`, which resolve by subdomain and stand down under `TOKEN_GROUPS`) must be off. It validates **in its constructor** on purpose — a half-usable resolution setup must abort the context refresh rather than serve requests that silently land in the wrong tenant.

Caches: `TenantExtractor.TENANT_CACHE` (by subdomain) and `TENANT_ID_CACHE` (provisioned tenants by id), both 10 min. Use `TenantExtractor.evictFromCaches(tenantId, subdomain)` after changing a tenant's registration or status; `TenantService.save/delete` already do.

## Tenant users (`core-tenants-users`, #7498)

Who belongs to a tenant under `TOKEN_GROUPS`, as this application knows it. Membership itself lives at the identity provider (groups `<tenantId>.<appId>.<role>`); an application can only *ask* for it, so this module keeps the record: who was invited, by whom, where each person stands.

- **Storage - a replica.** `DIRIGIBLE_TENANT_USERS` (`TenantUser`) - one row per tenant + email (lower-cased, the identity key; UK tenant + email): `status` `PENDING|INVITED|ASSIGNED|FAILED|REMOVED` (`REMOVED` is a hidden tombstone, so a late snapshot cannot resurrect the user), the provisioning system's `revision`, `invitedBy/At`, `lastChangedBy/At`, `lastErrorCode`/`lastErrorMessage` (why the latest change was not applied), and `lastSignInAt`. `DIRIGIBLE_TENANT_USER_ROLES` (`TenantUserRole`) - one row per role held or being added: `state` `GRANTED|ADDING|REMOVING`, `grantedBy/At` (null while `ADDING`); a role with no row is not held. **Only the external provisioning system writes the replica** (through the users snapshot endpoint), except `lastSignInAt`, the application's own observation of a sign-in; it holds states only, never a copy of the provisioning system's requests. SystemDB with an explicit tenant id (the tenant registry's pattern, so the machine caller writes without entering the tenant); every `TenantUserRepository` lookup carries the tenant id. The v1 tables `DIRIGIBLE_APPLICATION_USERS`/`_ROLES` are dropped by appended changesets - the replica is rebuilt by the next full resync.
- **The users snapshot endpoint** `PUT|GET services/tenant-provisioning/tenants/{tenantId}/users` (`TenantUserSnapshotEndpoint`) - the only writer of the replica. `PUT {complete, revision, users[]}` carries the users the external provisioning system changed (`complete: false`) or the tenant's full list (`complete: true`, its periodic resync), and `TenantUserReplicaService` applies it by five rules: a user is applied only when its `revision` is higher than the stored one (else counted `ignored`, still 200); an applied user replaces the row completely - status, who/when, the roles with their states, the last error - and keeps `lastSignInAt`; `REMOVED` drops the roles and keeps a hidden tombstone, and a newer live snapshot revives it with `lastSignInAt` cleared; a complete list tombstones every live row it does not name at or below its revision, stamped with that revision; an unknown email is inserted as sent. One transaction per user under a pessimistic lock, an insert race retried once; one 400 names every offending field (`TenantUserSyncValidation`). `GET [?includeRemoved=true]` is the replica for diagnostics. It exists exactly when the tenant provisioning API does (`TenantProvisioningApiEnabledCondition`), behind the same roles (`TenantProvisioningRoles`) and that API's `{status, error, message}` body.
- **The owner endpoints** `services/security/tenant-users` (`TenantUsersEndpoint`): `GET /context` (every authenticated user: `{enabled, tenantId, canManage, canRead, ownerRole, roles, caller}` - `caller` is the requester as the change requests record them, so a page can mark "you"), `GET` the live replica rows (`TenantUserView`, tombstones hidden), and three commands answered **202 `{requestId}`**: `POST {email, roles[]}` invite, `PUT /{id}/roles {roles[], expectedRevision}` set a member's roles (adding and removing in one change), `DELETE /{id} {expectedRevision}` remove (also the Dismiss of a `FAILED` row). **The platform publishes and reads; it never decides membership**: `TenantUserCommands` enforces the input (`INVALID_EMAIL`, `INVALID_ROLE`, `NO_ROLES`, `BAD_REQUEST`, `DEFAULT_TENANT`) and answers the business rules advisorily from the replica (`USER_NOT_FOUND` 404; `ALREADY_MEMBER`, `REQUEST_PENDING`, `NOT_A_MEMBER`, `STALE_REVISION`, `NO_CHANGE`, `LAST_OWNER` 409) - the provisioning system decides them again. Present only with `DIRIGIBLE_TENANT_USERS_ENABLED`; `TenantUsersConfigValidator` refuses to start without `TOKEN_GROUPS`, without a `global:` `DIRIGIBLE_TENANT_USERS_CHANGE_QUEUE`, without `DIRIGIBLE_TENANT_PROVISIONING_API_ENABLED` (nothing could write the list), or with only the v1 key `DIRIGIBLE_TENANT_USERS_REQUEST_QUEUE` set. The roles are constants, not configuration: `ApplicationRoles` (core-base, beside `Roles`) - `OWNER = "Owner"`, `USER = "User"`, `ALL` the ones an owner may grant. **The gate is the standard `@RolesAllowed`**: list for `Owner`/`DEVELOPER`/`ADMINISTRATOR`/`OPERATOR`, the commands for `Owner`/`DEVELOPER`/`ADMINISTRATOR`; the `AccessDeniedException`, a non-JSON body (415 - the CSRF defence; the routes declare no `consumes` so the refusal is answered in the endpoint's own shape) and an unreadable one (400) are answered as `{status, error, message, reason}`.
- **A change request** is the envelope `tenant.user.change.requested` v1 (`requestId, type, version, action INVITE|UPDATE_ROLES|REMOVE, tenantId, appId, email, roles` (the desired set, sorted; absent for `REMOVE`), `expectedRevision` (absent for `INVITE`), `requestedBy` (the requester's email), `requestedAt`), published by `TenantUserChangePublisher` with `MessageProducer` - synchronized, because the JMS session behind it is single-threaded; the business tenant travels in the payload because a `global:` destination is stamped with the default tenant. Nothing is written first and nothing is compensated: a broker refusal is a 503 `PUBLISH_FAILED`, and the replica changes only when the provisioning system reports what it did.
- **Sign-in tracking.** `TenantSelectionManager.selectTenant` - the one place the picker and the auto-selection of a user's only tenant go through - publishes a `TenantEnteredEvent` (core-tenants: tenant id, principal, the email claim). `TenantUserSignInListener` matches the replica row by email (the claim, else an email-shaped principal) and stamps `lastSignInAt` on an existing, not removed row only - the rows are the provisioning system's to create - in its own transaction and inside a try/catch: bookkeeping must never break a sign-in. Neither `enterTenant` (bearer) nor `ensureConsistent` (every request) publishes it.
- **Revocation.** A removed role takes effect at the person's next access-token refresh: `OAuth2SessionRevalidationFilter` refreshes the token, and `TenantSelectionManager.ensureConsistent` drops a selection whose group is gone (the person lands on the picker, or is refused without another tenant). Nothing here forces a refresh; the window is the access token's lifespan.
- Tests: `TenantUserReplicaServiceTest` (every apply rule), `TenantUserSyncValidationTest`, `TenantUserCommandsTest` (every reason code, the envelope per action), `TenantUserChangePublisherTest`, `TenantUsersAccessTest`, `TenantUsersConfigValidatorTest`, `TenantUserSignInListenerTest`; `TenantUserSnapshotApiIT` / `…DisabledIT`, `TenantUsersIT` (fabricated OIDC owner under `TOKEN_GROUPS`, the change requests received from the queue, the list written through the snapshot endpoint) / `TenantUsersDisabledIT`; the browser ITs against Keycloak `TenantUsersSettingsIT` (invite with two roles, a change followed while in progress, an edit in one save, a refused change's reason, a removal, the local last-owner refusal) and `TenantUsersSettingsHiddenIT`. The ITs play the provisioning system through `TenantUsersTestSupport` (tests-integrations: the machine authentication, the snapshot builder, the queue); `KeycloakTestContainer` changes an existing user's groups (`addUserToGroup`/`removeUserFromGroup`) and the realm's token lifespan.

## Integration clients (`core-tenants-clients`)

A tenant's external systems (a shop, a bank import, an accounting tool) call the application with an access token of their own (client credentials), without a person's session. Each such **integration client** belongs to exactly one tenant and holds the roles it was given there, never `Owner` and never a role of the instance. Only under `TOKEN_GROUPS`; under any other strategy no client is registered and an access token keeps its old rules.

- **The registry - written by the provisioning system.** `DIRIGIBLE_TENANT_CLIENTS` (`TenantClient`: tenant id, `clientId` (UK across tenants: a client belongs to one), `name`, the registry `revision` that last wrote the row, `createdBy/At`, `revokedBy/At`) and `DIRIGIBLE_TENANT_CLIENT_ROLES` (`TenantClientRole`, UK client + role). SystemDB with an explicit tenant id, like the user replica. The core-base interface `IntegrationClientRegistry.findActive(clientId)` (`base/tenant/clients/`) is what the security modules depend on; `TenantClientRegistryService` implements it.
- **`PUT|GET services/tenant-provisioning/tenants/{tenantId}/clients`** (`TenantClientsEndpoint`, the tenant provisioning API's roles, condition and `{status, error, message}` body). `PUT {revision, clients:[{clientId, name, roles[], createdBy, createdAt, revokedBy, revokedAt}]}` is always the tenant's **complete** registry, applied in one transaction under a pessimistic lock of the tenant's rows: a revision not higher than the stored one changes nothing (`applied: false`, still 200); every client named is inserted or updated, roles exactly as sent; a client not named is revoked; **a revoked client stays revoked** whatever a later registry says (a client id is never reused); a client id registered to another tenant refuses the whole registry (409). 400 names every problem (`TenantClientSyncValidation`): an active client holds at least one role, and `Owner`, `ADMINISTRATOR`/`DEVELOPER`/`OPERATOR` and `TENANT_PROVISIONER` are never given (`TenantClientRoles.FORBIDDEN`). Unknown tenant 404, a `DEPROVISIONING` one 409.
- **`GET services/tenant-provisioning/client-roles`** - the roles a client may be given: the application's registered roles (`RoleService`, e.g. the generated `<project>.<perspective>.<Entity>ReadOnly`/`FullAccess`) minus the forbidden ones. The provisioning system checks a request against it before it creates a client at the identity provider; the `PUT` itself does not refuse an unknown role, so a regeneration that renames roles never blocks a revocation.
- **Token acceptance** (`security-oauth2`, `IntegrationClients`). The client of an access token is `client_id` (Cognito, RFC 9068), else `azp` (Keycloak). The deployment's own clients - the ID and access token audiences, i.e. the login client and the provisioning system's machine client - are never looked up and behave exactly as before. Any other client is asked of the registry **on every request**: the audience check passes for an active registered client (`ResourceServerJwtSupport.ownClientsOrRegisteredClient`), and the converter turns it into an `IntegrationClientAuthenticationToken` named by the **client id** (what `CreatedBy`/`UpdatedBy` record) with **no authority at all** - nothing from its scopes - even when its token also carries the deployment's audience (a Keycloak audience mapper on a shared scope). A token that passed validation as a registered client only and is no longer known by the converter (revoked in between) is refused rather than falling back to its scopes. Both profiles pass the registry as an `ObjectProvider`, so a slim build without the module accepts no client.
- **Confinement** (`TenantSelectionFilter.serveIntegrationClient` → `TenantSelectionManager.enterTenantAsClient`). Every request of such a token must name its tenant in `X-Tenant-Id`, **on every path** (`shouldNotFilter` does not skip the platform's unfiltered prefixes for it): none → 403 `{reason: TENANT_REQUIRED}`; another tenant → 403 `NOT_A_MEMBER` (and a `TenantAccessRefusedEvent`); not provisioned here → 409. The request then runs in the tenant as `inItsTenant()`: the registry's roles and nothing else. It never runs in the default tenant.
- **Revocation** is the registry's: the next call after the `PUT` that revoked the client is a 401, whatever the token's lifetime. **Deprovisioning** deletes the tenant's rows (`TenantClientsTenantTeardown`, order 350).
- Tests: `TenantClientRegistryServiceTest` (every apply rule, the lookup), `TenantClientSyncValidationTest`, `ResourceServerJwtSupportTest` (the integration clients group), `TenantSelectionFilterTest`, `TenantSelectionManagerTest`; `IntegrationClientsIT` (mock identity provider, two provisioned tenants: the registered client in its tenant with its role and not its scopes' roles, refused without the header, on another tenant and on a role it lacks, revoked on its next call and not revived by a late registry, the forbidden roles, `client-roles`, one tenant per client).

## Initializing a new tenant touches that tenant only (#7799)

Activating a tenant (`POST services/tenant-provisioning/tenants/{id}/activation`) and the built-in `TenantsProvisioner` both call `TenantPostProvisioningStep.execute(Set<String> tenantIds)` with the tenants they just activated or provisioned. The `default` of that overload runs the old no-argument `execute()`, so a step that cannot tell tenants apart keeps working. `RetriggerSynchronizersTenantPostProvisioningStep` implements it as `SynchronizationProcessor.initializeTenants(ids)`. **Do not go back to blanking the checksums of every per-tenant definition** (the no-argument `execute()` still does, for external callers). That re-ran every multitenant artefact for every tenant: every tenant's tables were altered again, seed rows a tenant had deleted were re-imported, and one tenant's failure was reported for all of them.

- **The scoped pass.** `initializeTenants` claims the same `processing` slot as a full pass, waiting (bounded) for the boot pass. It re-reads the artefacts of the `PARSED` multitenant definitions, sets them `NEW`/`CREATE` in memory, and runs the full pass's phase machinery (`completeArtefacts`) inside `TenantContext.executeScopedTo(ids, …)`. That restricts every per-tenant fan-out reached on the thread to those tenants: `BaseSynchronizer`'s fan-out and `MigrationsSynchronizer`'s own loop alike.
- **Two fan-outs (#8477).** `executeForEachTenant` visits the `PROVISIONED` tenants (and the default one) - every **runtime** caller uses it: the outbox relay, the client-Java consumers' top-up, the reconciliation passes. `executeForEachMaintainedTenant` visits the `PROVISIONED` **and `SUSPENDED`** ones - every **synchronizer** phase uses it (`BaseSynchronizer`'s complete and cleanup, `MigrationsSynchronizer`), and so does `FlowableProcessesInitializer`'s deploy of the system processes, so an application version published while a tenant is suspended still reaches its schema. Both honour `executeScopedTo`. A synchronizer that starts runtime decides per tenant through `TenantContext.isSuspended`: `JobsManager.scheduleJob` pauses a suspended tenant's user job as soon as it is scheduled (also on its "already exists" path), and `ListenerSynchronizer` only registers a suspended tenant's listener (`ListenersManager.registerListener`, which refuses a missing handler as a start would) without starting it. A new synchronizer fan-out uses the maintained variant; a new runtime fan-out does not. The shared artefact rows are written back as they were afterwards (`SharedState.restore`), because jobs and listeners save the row directly while they complete it.
- **Outcomes are per tenant.** `DIRIGIBLE_TENANT_ARTEFACTS` (`TenantArtefactLedgerService`, core-initializers, behind the core-base `TenantArtefactLedger`) holds one row per (artefact, tenant). `BaseSynchronizer.completeInternal` writes a tenant's row when a phase changed its lifecycle, or failed it without a state; a phase that did nothing for the tenant records nothing. `MigrationsSynchronizer` writes its own rows. A shared row that the last tenant left successful while an earlier tenant failed is set `FAILED` ("Failed for tenant(s) …", #7776). The rows of a cleaned-up artefact are forgotten.
- **Status.** `DIRIGIBLE_TENANT_INITIALIZATIONS` (`TenantInitialization`, core-tenants-provisioning) is opened `REQUESTED` in the request thread, before the 202. That makes the tenant read `IN_PROGRESS` on every node until its own run ends (`RUNNING`, then `FINISHED` with the run's error, if any). An open record is resumed on `ApplicationReadyEvent`. `TenantInitializationStatusCalculator` reads that record, the tenant's ledger failures and the global `BROKEN` definitions, and never another tenant's rows. Tenants activated together are initialized one after the other, each on its own.
- **Guards:** `SynchronizationProcessorTenantInitializationTest`, `BaseSynchronizerTenantOutcomesTest`, `TenantContextImplTest`, `TenantActivationServiceTest`, `TenantInitializationStatusCalculatorTest`, `TenantsProvisionerTest`. `TenantScopedInitializationIT` (three externally provisioned tenants: a deleted seed row stays deleted while another tenant activates, and a broken tenant's `FAILED` is neither spread nor hidden).

## Deprovisioning a tenant (`core-tenants-provisioning`, #7933)

`DELETE services/tenant-provisioning/tenants/{id}` (`TenantProvisioningEndpoint` → `TenantDeprovisioningService`, the API's roles) removes a tenant and everything this application holds of it, **synchronously and idempotently**:

- **Status first.** The tenant is moved to `TenantStatus.DEPROVISIONING` and saved before anything is torn down. `executeForEachTenant` reads `PROVISIONED` tenants only, so from that moment no synchronizer fan-out, client-Java top-up or reconciliation pass, outbox relay or job reaches it - across a restart too. No in-memory marker exists, by design. `TenantUserReplicaService` answers **409** for such a tenant. `TenantActivationService.activate` and `TenantDataSourceRegistrationService.register` refuse it with 409.
- **Then every `TenantTeardownParticipant`** (core-base, `order()` + `teardown(tenantId)`, idempotent - finding nothing is success), lower order first:
  - **100**, what runs for the tenant:
    - `JobsTenantTeardown` deletes the Quartz jobs `<id>###*` of group `defined` and the tenant's job logs;
    - `ScheduledClassConsumer` forgets its `(job, tenant)` bookkeeping, so a tenant re-registered under the same id is topped up again;
    - `ListenerClassConsumer` closes the tenant's `@Listener` handles and its shared connection;
    - `ListenersTenantTeardown` stops the `.listener` consumers on `<id>###*`;
    - `BpmTenantTeardown` cancels the tenant's process instances, then deletes their history.
  - **200**, `TenantDataSourceTenantTeardown`: the `<id>_DefaultDB` data source. `DataSourceService.delete` → the lifecycle listener → `removeInitializedDataSource` closes the pool synchronously.
  - **300**, `TenantUsersTenantTeardown`: the user replica. The role rows cascade, and `TENUSER_TENANT_ID` has no foreign key, so the rows would otherwise be orphaned.
  - **350**, `TenantClientsTenantTeardown`: the integration client registry, the same way. From then on the tenant's clients are refused (401), whatever their tokens' lifetime.
  - **400**, `TenantInitializationTenantTeardown`: the `DIRIGIBLE_TENANT_INITIALIZATIONS` row.
  - **500**, `TenantArtefactLedgerTenantTeardown`: the artefact ledger rows.
  - **600**, the tenant's content: the intent conversations, the traced task states, and the tenant's CMS documents - one participant per provider, each a no-op unless its provider is the configured `DIRIGIBLE_CMS_PROVIDER`:
    - `CmsInternalTenantTeardown`: the folder `<root>/<id>`, deleted recursively, so it must resolve to a direct child of the CMS root or the participant refuses;
    - `CmsS3TenantTeardown`: every object under `<id>/` in the shared bucket. The facade prefixes paths with the *current* tenant and the request runs as the default tenant, so it deletes `/` inside `TenantContext.execute(id, …)`; `S3Facade.deleteFolder` deletes in batches of 1,000;
    - `CmsSharepointTenantTeardown`: the folder `<id>` of the shared document library, the same way. A missing folder is success. The Graph delete moves it to the site's recycle bin, where the site's retention applies.
- **Last**, the tenant's `DIRIGIBLE_USERS` and the tenant row (`TenantService.delete` evicts the resolution caches).
- **Answers:**
  - `204` for a removed tenant **and** for an unknown one, so a 404 from this route can only mean the route is missing;
  - `409` while the tenant's initialization is open, bounded by `DIRIGIBLE_TENANT_PROVISIONING_DEPROVISION_ACTIVATION_STALE_MINUTES` (default 30);
  - `400` for an invalid id or the default tenant;
  - `500` naming the participant that failed. The tenant stays `DEPROVISIONING` and the repeated call resumes it.
- **Not touched:**
  - the tenant's data schema and its database user - the provisioner's, dropped by it after the 204;
  - broker destinations and durable subscriptions;
  - the shared process definitions;
  - `DIRIGIBLE_CROSS_TENANT_AUDIT`, a security audit trail;
  - the S3 bucket and the SharePoint document library themselves - every tenant shares them; nor is the SharePoint recycle bin purged.
- **A suspended tenant can be deprovisioned.** The teardown deletes its paused jobs and its stopped listeners as any others; Flowable deletes a suspended process instance with its suspended jobs (`BpmTenantTeardownTest#deletesSuspendedInstances`, a real engine), so `BpmTenantTeardown` needs no activation first.
- **Single instance.** The runtime teardown acts on the instance that answers, so an application is expected to run as one instance.
- **Tests:** `TenantDeprovisioningServiceTest` (order, unknown, default tenant, 409 and its bound, a failure that resumes), `JobsTenantTeardownTest`, `BpmTenantTeardownTest`, `CmsInternalTenantTeardownTest`, `CmsS3TenantTeardownTest`, `CmsSharepointTenantTeardownTest`, `TenantPathResolverTest`, `S3FacadeDeleteFolderTest` (+ the LocalStack `S3FacadeTest`), `ListenersManagerTest#stopTenantListenersStopsOnlyTheTenantsOwn`, `TenantActivationServiceTest`, `TenantUserReplicaServiceTest`; `TenantDeprovisioningIT` (two externally provisioned tenants with a table, a job and a process: one is removed, the other keeps everything, and nothing comes back on the next synchronizer pass), `TenantProvisioningApiDisabledIT`.

## Suspending a tenant (`core-tenants-provisioning`, #8477)

`PUT services/tenant-provisioning/tenants/{id}/status` with `{"status": "SUSPENDED" | "PROVISIONED"}` (`TenantProvisioningEndpoint` → `TenantSuspensionService`, the API's roles, condition and error body) pauses a tenant - a subscription whose payment failed - and resumes it, **without touching its data**. It answers `200` with the same `TenantProvisioningState` as `GET …/tenants/{id}`.

| From \ asked | `SUSPENDED` | `PROVISIONED` |
|---|---|---|
| `PROVISIONED` | suspend → 200 | the resume half again → 200 |
| `SUSPENDED` | the suspend half again → 200 | resume → 200 |
| `INITIAL`, `PENDING_ACTIVATION`, `DEPROVISIONING` | 409 | 409 |
| unknown tenant | 404 | 404 |
| default tenant, invalid id, any other status | 400 | 400 |

- **`TenantStatus.SUSPENDED` is the only marker** - no in-memory flag, by the rule `DEPROVISIONING` follows.
- **Suspend: the status first.** The tenant is saved `SUSPENDED` (which evicts the resolution caches, so access is refused from the next request on), then every `TenantSuspensionParticipant` (core-base: `order()`, `suspend(id)`, `resume(id)`, a default no-op `resumed(id)`) runs `suspend`, lower order first. Participants stop the runtime and delete no definition; both halves are idempotent and finding nothing is success:
  - `JobsTenantSuspension` (engine-jobs) pauses every Quartz job `<id>###*` of group `defined` - `.job` artefacts and client-Java `@Scheduled` alike; a paused trigger survives a restart in the JDBC store. Job logs stay.
  - `ListenersTenantSuspension` (engine-listeners) stops the `.listener` consumers (`stopTenantListeners`); resume runs `ListenersManager.startTenantListeners`, which starts the tenant's consumer of every listener artefact that is not running, skipping global destinations (never stopped) and `FAILED`/`FATAL` artefacts (the synchronizer's retry owns them), and throws naming any it could not start.
  - `ListenerClassConsumer` / `ScheduledClassConsumer` (engine-java) suspend with their teardown code (close the tenant's handles and shared connection / forget the `(job, tenant)` bookkeeping); `resume` sets their incomplete flag and `resumed` - called once the tenant is `PROVISIONED` again - runs `reconcile()`, so the top-up reaches it at once instead of at the reconciler's next tick.
  - `BpmTenantSuspension` (engine-bpm-flowable) suspends the tenant's active process instances; Flowable moves their timer and async jobs to the suspended-job table. Resume activates every suspended instance of the tenant - no other platform path suspends an instance (a retired deployment suspends its *definition*; an instance of a retired definition activates fine). A definition's **timer start event** is not an instance and keeps its schedule - not covered.
- **Resume: the participants first, in reverse order, while the tenant is still `SUSPENDED`; then it is saved `PROVISIONED`; then every `resumed` hook** (whose failure is logged, not answered: the tenant is running, and the hook's own reconciliation catches up).
- **A participant that throws answers 500 naming it**; the tenant stays `SUSPENDED` in both directions (the safe side - still refused) and the repeated request finishes the run.
- **Access** (security-oauth2): `TenantSelectionException.Reason.SUSPENDED` → 409 for `selectTenant`, `enterTenant` and `enterTenantAsClient`; `ensureConsistent` drops a held selection; `TenantOption.State.SUSPENDED`; see Tenant selection. `TenantExtractor` and the default-tenant fallback are unchanged: a suspended tenant is never resolved.
- **Not paused:** its data source and pool, its data, its user replica (`PUT …/users`), its client registry (`PUT …/clients`), its CMS documents and its initialization record - the provisioner keeps writing the replica and the registry. The outbox relay skips it through `executeForEachTenant`; its rows wait and are relayed after the resume. Messages to its queues and durable subscriptions wait on the broker.
- **Maintained, not run:** the synchronizers reach it through `executeForEachMaintainedTenant` (see the initialization section), so a published schema change reaches it while it is suspended.
- **Other routes:** `POST …/activation` and `PUT …/datasources/default` answer 409 for a suspended tenant (`TenantActivationService`, `TenantDataSourceRegistrationService`); `DELETE` removes it (see Deprovisioning). `TenantInitializationStatusCalculator` reports a suspended tenant's initialization as it was, not `NOT_STARTED`.
- **Single instance**, as for deprovisioning.
- **Tests:** `TenantSuspensionServiceTest` (the table cell by cell, the orders, a failure in each direction finished by a repeat), `JobsTenantSuspensionTest`, `JobsManagerSuspendedTenantTest`, `BpmTenantSuspensionTest` (a real in-memory Flowable), `BpmTenantTeardownTest#deletesSuspendedInstances`, `ListenersManagerTest#startTenantListenersStartsOnlyTheTenantsOwn`, `ListenerSynchronizerRetryTest`, `TenantContextImplTest`, `TenantSelectionManagerTest`, `TenantSelectionFilterTest`, `TenantActivationServiceTest`; `TenantSuspensionIT` (keycloak profile + mock identity provider, two externally provisioned tenants: the suspended one's bearer user and integration client get `409 SUSPENDED`, its job is paused, its client-Java queue listener consumes nothing and its timer does not fire while the other tenant's do; a published column reaches it; resumed, the waiting message is consumed, the timer fires and its rows are unchanged; suspended again it is deprovisioned; the route's 400/404/409/403/401).

## The tenant's Owner manages its tenant-scoped settings (#7877)

Document numbering (`DocumentNumberEndpoint`), tenant configuration (`TenantConfigurationsEndpoint`) and the print template catalogue's read/write/duplicate/delete (`PrintEndpoint`) admit `ApplicationRoles.OWNER` beside `ADMINISTRATOR`/`OPERATOR`, through the same `@RolesAllowed` as Settings → Users. Everything they touch already belongs to the current tenant, and under `TOKEN_GROUPS` the `Owner` authority exists only for the selected tenant (`TenantSelectionManager.ensureConsistent` recomputes it from the groups on every request), so an owner of A is refused B's settings: B cannot be selected without a group in it, and selecting it as a `User` of B leaves no `Owner` authority. Instance-wide keys stay with staff (see REST below). The application shells already list Tenant Configuration and Document Numbering for everyone and the shared `printTemplates` store offers Print Templates when its read of the tenant configuration answers 200 (`canManage`) and a document type exists - in the platform shells and in every generated shell - so an owner sees all three next to Users without a shell change. Guards: `TenantConfigurationsEndpointTest`, `TenantOwnerSettingsIT`.

## Tenant-aware configuration (`commons-config` + `core-configurations`)

Each tenant can override selected configuration values; overrides are resolved **per request**, scoped to the current tenant. Added on PR [#6205](https://github.com/eclipse-dirigible/dirigible/pull/6205).

**Resolution precedence** (in `Configuration.get`): `RUNTIME (set() programmatic) → tenant thread map → ENVIRONMENT (env + sys props) → DEPLOYMENT (.properties) → MODULE`. The tenant map sits between the runtime variables and the environment, so a tenant override beats env/properties but a programmatic `Configuration.set` still wins.

**Layering is load-bearing — do not break it.** `modules/commons/commons-config` sits at the bottom of the dependency graph and must stay dependency-free. It carries **only** the neutral mechanism: a `ThreadLocal<Map<String,String>>` in `Configuration` with `setThreadConfiguration` / `removeThreadConfiguration` / `getThreadConfiguration`, plus the `get()` precedence branch. It has **no** knowledge of tenants, DB, or where the values come from. Everything tenant/DB/policy-related lives one layer up in `components/core/core-configurations` (which depends on `data-sources`; `TenantContext` comes from `core-base`). Never add a tenant/DB dependency to `commons-config`.

- **Store** (`tenant/TenantConfigurationStore`) — raw `SqlFactory` CRUD against `DataSourcesManager.getDefaultDataSource()`, which inside a tenant scope is auto-routed to that tenant's schema, so a distinct **`DIRIGIBLE_CONFIGURATIONS`** table (columns `CONFIGURATION_KEY` / `CONFIGURATION_VALUE`) lives per tenant schema; created create-if-absent on first use.
- **Cache** (`tenant/TenantConfigurationCache`) — per-tenant map, loaded on first access, invalidated on write. Per-node only; a multi-node cluster would need an external invalidation signal (documented as out of scope).
- **Key policy** (`tenant/TenantConfigurationKeyPolicy`) — an **explicit white-list of full keys (exact match, NO wildcards)**; default-deny for everything else, so a tenant can never shadow infrastructure keys. The list is not written in the policy: it is the `DirigibleConfig` entries marked `meta().tenant(order)`, in that order (`DirigibleConfig.tenantOverridableKeys()`, #7759) - the **branding** keys (`DIRIGIBLE_BRANDING_{NAME,SUBTITLE,BRAND,BRAND_URL,FAVICON,THEME,PREFIX,ANALYTICS}`), `DIRIGIBLE_APPLICATION_{LANGUAGES,COUNTRY}`, `DIRIGIBLE_DOCUMENTS_EXT_CONTENT_TYPE_MS_ENABLED`, `DIRIGIBLE_CMS_ROLES_ENABLED`, `DIRIGIBLE_APP_BASE_URL` and the mail identity `DIRIGIBLE_MAIL_{SENDER,REPLY_TO}` (#7878 - the From and Reply-To of an application's own mail; the SMTP account, `DIRIGIBLE_MAIL_{USERNAME,PASSWORD,SMTP*,SMTPS*,TRANSPORT_PROTOCOL}`, stays the instance's and is not overridable). To widen, mark concrete entries — do not reintroduce prefix/wildcard matching (that was explicitly rejected) and do not reintroduce a configurable `DIRIGIBLE_TENANT_CONFIGURATION_ALLOWED_KEYS` (removed). A non-allow-listed key can still be *stored* but is never injected. **The one prefix exception is `ALLOWED_PREFIXES` = `DIRIGIBLE_PRINT_TEMPLATE_`** (#7755): the print template a document type prints with is one key per document type and language (`DIRIGIBLE_PRINT_TEMPLATE_<ENTITY>_<LANG>`), and the document types are whatever the tenant's applications declare, so the family cannot be enumerated in code. The prefix is literal (no pattern), names a family of keys that only ever select a print template - nothing infrastructure-shaped can start with it - and a bare prefix is not a key (`isPrefixed`). Its members are injectable but deliberately NOT returned by `/predefined` (they have their own page, Settings > Print Templates; the shells save every listed entry back on Save, which would undo a selection made elsewhere meanwhile). A new prefix needs the same argument - a family keyed by user-declared objects - not convenience.
- **Request wiring** (`tenant/TenantConfigurationInitFilter`, `@Order(LOWEST_PRECEDENCE)`) — runs downstream of the Spring Security filter chain, i.e. **inside** the tenant execution scope established by `core-tenants`' `TenantContextInitFilter`; it loads the allow-listed entries into the thread map for the request and clears them in `finally`. **Do not move this into `TenantContextInitFilter`** — that would force `core-tenants` to depend on `core-configurations` (cycle). Keep it in `core-configurations`.
- **Work that is not a request** - a listener dispatch, a job fire, a process step - runs in its tenant's scope but passes no filter, so it reads the instance value of every overridable key unless its entry point loads the overrides: `ListenerClassConsumer` does it for `@Listener`/`MessageHandler` dispatches, `JobHandler` (every Quartz fire) and `DirigibleJavaCallDelegate` (`${JavaTask}`, the intent `Send` step) through `TenantConfigurationScope.executeWithTenantOverrides` (a `core-base` interface `TenantConfigurationService` implements, taken through an `ObjectProvider` - an engine must not depend on `core-configurations`: `core-initializers` depends on `engine-jobs`, so such a dependency reaches `core-tenants` and nearly every module, and puts the request filter into test contexts whose `TenantContext` is a bare mock), which loads them only when the thread carries none and clears them afterwards (#7878; before it a job's or a process's notify mail went out from the instance's sender with the instance's `{appUrl}`). `PrintFacade` loads them the same way for a render outside both. A new entry point that runs client code for a tenant does the same.
- **REST** (`endpoint/TenantConfigurationsEndpoint`, the tenant's `Owner` or `ADMINISTRATOR`/`OPERATOR`) at `services/core/configurations/tenant`: `GET` (stored entries), `GET /predefined` (every allowed key with the tenant's value or `null`), `PUT` `{key,value}`, `DELETE ?key=`. An `Owner` who is not staff manages the allow-listed keys only: a `PUT`/`DELETE` of any other key is 403 and `GET` leaves those keys out (`TenantConfigurationService.isTenantOverridable`).
- **UI**: a built-in **Tenant Configuration** entry in the Harmonia **application shell** Settings (`components/resources/resources-application` — `views/_settings.html` + `js/appShell.js`), rendered locally like Region & Language: lists the predefined branding props with editable values (empty → platform default), Save/Reload, 403 → permission notice. A generic AngularJS CRUD view also exists in `components/ui/view-configurations` (`tenant-configurations.html`) for arbitrary keys.

**Making a new property tenant-overridable (the whole recipe):**

1. **Mark the key's entry** in `modules/commons/commons-config/.../DirigibleConfig.java` with `meta().tenant(<order>)` (add the entry first if the key is not catalogued) - the order is its position in the tenant settings. No new prefixes (see the print template exception above), no wildcards: `TenantConfigurationKeyPolicy.ALLOWED_KEYS` is derived from these marks. This single edit is all that is functionally required: the key becomes injectable, is returned by `GET /services/core/configurations/tenant/predefined`, and **appears automatically** in the Harmonia Settings "Tenant Configuration" page (the page is data-driven from `/predefined`) and in the REST/AngularJS management surfaces.
2. **Read it at request time.** The override only takes effect for code that calls `Configuration.get("<KEY>")` (or `DirigibleConfig.<X>.getStringValue()`) **during a request, inside the tenant scope**. A value read once at boot or cached in a bean/`static` field will not reflect per-tenant overrides — read it lazily per use. (Branding already works because the branding services read it live.)
3. **Label (optional).** The Settings page derives a display label in `appShell.js` `tenantConfigLabel()`, which strips the `DIRIGIBLE_BRANDING_` prefix. For a non-branding namespace, extend that helper so the label reads nicely; otherwise it falls back to a de-prefixed, title-cased form of the key.
4. **Tests.** Add the key to `TenantConfigurationKeyPolicyTest` (allowed set) and to the ordered list in `DirigibleConfigCatalogueTest` and, if you want end-to-end coverage, mirror `TenantConfigurationIT` (set → resolve with precedence → clear).

Do **not** widen by reintroducing wildcards or a config-driven allow-list — the explicit in-code white-list is deliberate (a tenant must never be able to shadow infrastructure keys). The `DIRIGIBLE_PRINT_TEMPLATE_` prefix is the single, argued exception, not a precedent.

**SqlFactory quoting gotchas (bit this feature twice):** the `create().table()` builder takes **pre-quoted** identifiers (the `TableCreateProcessor` pattern), while `select/insert/update/delete` and the `where(...)` condition **auto-quote** — pass **unquoted** names there. A VARCHAR length arg must include its own parens: `column(..., "(255)")`, not `"255"` (renders `VARCHAR (255)`).

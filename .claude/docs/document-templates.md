## Document templates (`parsers/document` + `engine-document`) — print to PDF

A lightweight declarative document-template engine for printable business documents (invoice, order, receipt, ...), merged 2026-07-02 via PRs [#6118](https://github.com/eclipse-dirigible/dirigible/pull/6118) (parser library) and [#6119](https://github.com/eclipse-dirigible/dirigible/pull/6119) (platform arc). Four cooperating layers:

- **`modules/parsers/document`** (`dirigible-parsers-document`, pure library, zero deps) — the XML-like DSL: hand-written parser (business-user lenient: raw `&` is literal, Mustache `{{...}}` survives verbatim, exact line/column errors), sealed `Node` AST (one record per tag + `CustomNode`/`TagRegistry.register` extension), layout primitives (`Measurement` `100/100px/50%/*/2*/auto`, `Alignment`), `DataBinder` (map-context `{{path}}` merge; `table`/`for` `source` lists expand to rows with row-scoped fallback; `if` truthiness; unresolved → empty; **`{{A|B}}` alternative operands** — first non-blank wins, left to right, the last one rendered whatever it holds, so an optional twin field never leaves a hole in a legal document; **floats print as `### ### ### ##0.00`** — the form pages' money pattern; **`{{Total:words(<currency>)}}` spells the amount out** in the template folder's language, Bulgarian and English ([#7494](https://github.com/eclipse-dirigible/dirigible/issues/7494)), empty wherever it cannot), and `XslFoRenderer` (bound layout tree → self-contained XSLT/XSL-FO stylesheet for the FOP `PDFFacade` — the platform's only PDF path). Grammar/EBNF + gotchas in the module README.
- **`engine-intent`'s `PrintIntentGenerator`** (@Order(800)) — Generate emits a standard `<Entity>.print` per document (header-items) master at the project root; `.print` is an intent-owned (scrubbed) extension. Data contract: `{{document.<PascalProp>}}` + `<table source="items">` with `{{<PascalProp>}}` cells.
- **`components/engine/engine-document`** — the runtime: `PrintTemplateSynchronizer` (multitenant) seeds the published template into every tenant's CMS as an **immutable version** `Templates/<Entity>/Print/<lang>/standard@<version>.print` beside the earlier ones (#7755) — tenant templates (`<name>.print`, no `@`) are the editable customisations and are never touched, the active one is the tenant configuration `DIRIGIBLE_PRINT_TEMPLATE_<ENTITY>_<LANG>` (else the version of `standard` the registry ships now), versions are ordered and kept immutable by the ledger `DIRIGIBLE_PRINT_TEMPLATE_VERSIONS`, and deleting the artefact never touches the CMS - read `components/engine/engine-document/CLAUDE.md` before changing any of it (the migration never uses the CMS rename, which S3 does not implement); all of it is `PrintTemplateCatalog`'s knowledge, the CMS stays a plain file store; `PrintEndpoint` — `GET /services/print/{entity}/languages` (CMS language folders, `Locale` display names) and `POST /services/print/{entity}?lang=` (`{document, items}` JSON → parse → bind → XSL-FO → `application/pdf`). The **client supplies the data** it already loaded (no server-side entity fetching/auth forwarding); dropdown FKs arrive as display labels.
- **Harmonia document view** — a Print button (edit-only, footer toolbar): one CMS language with at most one tenant template prints directly; several languages or several tenant templates open a dialog ("English" → en, then the layouts of that language - its tenant templates and the shipped default - preselected to the active one), shared by every generated page through `application-core/shell/js/components/printActions.js`. Multilanguage = upload templates under more `Templates/<Entity>/Print/<lang>/` folders. Settings → Print Templates previews, selects (or goes back to the default), duplicates, edits, compares and deletes: in the IDE perspective (`settings-print-templates`) and - the same capability for a tenant admin who never sees the IDE - in every platform shell and every generated application shell (`application-core/shell/views/_print-templates.html` + `stores/printTemplates.js`, see shells.md).

**Images** (issue [#7024](https://github.com/eclipse-dirigible/dirigible/issues/7024)): `<image src="...">` is resolved server-side by `engine-document`'s `PrintImageResolver` and **inlined as a `data:` URI**, so the same template renders identically in all three paths (Print button, `attach: print`, `function: Snapshot`) - a `data:`/`scheme:` source is emitted unchanged, anything else is a path in the tenant CMS. Every failure is soft (missing, oversized past `DIRIGIBLE_PRINT_IMAGE_MAX_SIZE` = 2 MB, not `image/*`, `..` in the path): the image is omitted, never a broken-image box. The generated scaffolds carry ONE shared logo slot, `Templates/Print/logo.png` - a company has a logo, not a per-document one, so branding a deployment is a single upload. A file of the record itself needs no new modeling: an Attachment row's `StoragePath` is a CMS path, so `{{document.<Relation>.StoragePath}}` is a valid `src`. The parser library stays storage-free - it takes an `ImageResolver` (`renderer.ImageResolver`, default `PASS_THROUGH`).

**Detailed guide:** [`components/engine/engine-document/CLAUDE.md`](components/engine/engine-document/CLAUDE.md). Renderer v1 limits (documented, deliberate): header/footer render once in-flow (not repeated page regions), `repeatHeader`/`pageBreak` ignored, 1px = 1pt, a data-less table is skipped (FOP rejects empty table bodies).

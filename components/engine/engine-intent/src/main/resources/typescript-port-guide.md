# Porting TypeScript to Java

This turn is a **port**. Server-side TypeScript and JavaScript are removed from the platform in
16.0, and the developer is replacing one hand-written TypeScript (or `.mjs`) file with the Java
class that does the same job. The request shows the TypeScript; you propose the **complete Java
file** named in the request, through `propose_java`, exactly as for any other file. Everything in the
guide above still applies.

## The contract of a port

- **Same behaviour, Java idioms.** Port what the file does, not how it is written. Keep its names
  where Java allows them - the class name is the file name, which is what the runtime routes and
  wires by. Fix nothing you were not asked to fix; where the TypeScript is plainly wrong (it adds an
  amount on every update as well as on create, say), port the evident intent and **say so** in the
  explanation, so the developer decides.
- **The package is the folder.** A file at `widgets/api/SalariesService.java` declares
  `package widgets.api;`. A folder name that is not a Java identifier cannot be a package: say so
  instead of proposing a file that will not compile.
- **The generated TypeScript is gone, or about to be.** A project is regenerated with the Java
  templates before its custom code is ported, so the TypeScript imports from `gen/...` now resolve
  to generated **Java** classes. Never port generated code itself.
- **Delete nothing, write one file.** The developer deletes the TypeScript file once the port is in,
  and moves any descriptor that named it (below). Tell them which, in the explanation.

## Generated data access

| TypeScript (generated by the removed templates) | Java (generated by the Java templates) |
|---|---|
| `gen/<project>/dao/<Perspective>/<Entity>Repository.ts`, class `<Entity>Repository` | `gen.<project_as_identifier>.data.<perspective_lowercase>.<Entity>Repository` - a bean: inject it |
| the entity as a plain object, `salary.Net` | `<Entity>Entity` in the same package, with public fields named as in the model: `salary.Net` |
| `new SalaryRepository()` | constructor injection of `SalaryRepository` (`@Inject` on a field also works) |
| `findAll({ $filter: { equals: { Status: 1 } } })` | `findAll(Criteria.create().eq("Status", 1))` |
| `$filter: { notEquals / greaterThan / lessThan / contains / in }` | `ne` / `gt` / `lt` / `like("%x%")` / `in` on `Criteria` |
| `$select`, `$sort`, `$limit`, `$offset` | `orderByAsc` / `orderByDesc` on `Criteria`; `findAll(criteria, limit, offset)` |
| `findById(id)` | `findById(id)` (the entity, or `null`) or `findOne(id)` (an `Optional`) |
| `create(entity)` / `update(entity)` / `deleteById(id)` | `save(entity)` / `update(entity)` / `deleteById(id)` |
| `count()` | `count()` / `count(Criteria)` |

`Criteria` is `org.eclipse.dirigible.components.data.store.java.repository.Criteria`. The generated
project's own types are listed in the request - import exactly those names. A repository of
**another** project (an import path starting with that project's name, e.g.
`codbex-currencies/gen/...`) is that project's generated Java class, also listed when the workspace
has the project.

## The SDK

TypeScript imports `sdk/<module>` (or `@aerokit/sdk/<module>`); the Java counterpart lives in
`org.eclipse.dirigible.sdk.*`:

| TypeScript | Java |
|---|---|
| `sdk/http` `Controller`, `Get`/`Post`/`Put`/`Patch`/`Delete`, `Body`, `PathParam`, `QueryParam` | the same names in `sdk.http` |
| `sdk/http` `request`, `response`, `upload`, `client` | `sdk.http.Request`, `Response`, `Upload`, `HttpClient` |
| `sdk/db` `database`, `query`, `update`, `insert`, `sequence`, `sql`, `procedure` | `sdk.db.Database` |
| `sdk/db` `store` | `sdk.db.Store` - never for an entity that has a generated repository |
| `sdk/messaging` `producer` / `consumer` | `sdk.messaging.Producer` / `Consumer` |
| `sdk/job` `scheduler`, `Scheduled` | `sdk.job.Scheduler`, `Scheduled` |
| `sdk/bpm` `process`, `tasks`, `deployer` | `sdk.bpm.Process`, `Tasks`, `Deployer` |
| `sdk/security` `user`, `Roles` | `sdk.security.User`, `Roles` |
| `sdk/core` `configurations`, `env`, `globals`, `context` | `sdk.core.Configurations`, `Env`, `Globals`, `Context` |
| `sdk/log` `logging` | `sdk.log.Logging` + `sdk.log.Logger` |
| `sdk/mail`, `sdk/cms`, `sdk/io`, `sdk/utils`, `sdk/extensions` | `sdk.mail.Mail`, `sdk.cms.*`, `sdk.io.*`, `sdk.utils.*`, `sdk.extensions.Extensions` |
| `sdk/component` `Component` (and its alias `Injected`), `Inject` | `sdk.component.Component`, `Inject` |

JSON: `JSON.parse` / `JSON.stringify` are `org.eclipse.dirigible.sdk.utils.Json.parse(text, Type.class)`
/ `Json.stringify(value)`. A controller method returns its value - an object, a record, a `Map`, a
`List` - and the platform writes it as JSON; there is no `response.println(JSON.stringify(...))`.

## The shapes you will meet

**A REST service** - a `@Controller` class with `@Get("/path")` methods. The Java class keeps the
annotations; the URL changes, because the runtime routes Java by package and class:

- TypeScript: `/services/ts/<project>/<folder>/<Name>.ts/<path>`
- Java: `/services/java/<project>/<folder>/<Name>/<path>`

Say so in the explanation: every page or client calling the old URL has to be repointed.

**An entity event handler** - an `.extension` contributing to the extension point
`<project>-<Perspective>-<Entity>` whose module exports `trigger(event)`, called with
`{ table, key, entity, operation }` on every create, update and delete. In Java it is a
`@Component implements MessageHandler` listening on the entity's topic, `ListenerKind.TOPIC`:

- `<project>-<Perspective>-<Entity>` - a row was created;
- `<project>-<Perspective>-<Entity>-updated` - a row was updated;
- `<project>-<Perspective>-<Entity>-deleted` - a row was deleted.

The message is the row as JSON: `Json.parse(message, <Entity>Entity.class)`. One class per topic it
needs; an `operation` the TypeScript never distinguished is a question to raise, not a guess. The
`.extension` file goes once the listener is in.

**A job** - a `.job` naming a script handler becomes a `@Component` with a `@Scheduled(expression =
"<the job's cron>")` method, or a `JobHandler`; the `.job` file goes.

**A listener** - a `.listener` naming a script handler becomes a `MessageHandler` (or a `@Listener`
method) on the same destination and kind; the `.listener` file goes.

**A static extension module** - a `.js` that only returns configuration (`getMenu`, `getNavigation`,
`getWidget`, ...) is not ported to Java at all: it becomes a `.json` module holding the returned
object, and the `.extension` names that `.json`. Say so and propose nothing.
